# Object Type Variants

## Problem

### Current State of Things

Right now, we have distinct types of objects (see @src/shared/object/maps/objectTypeConfigMap.ts ), each of which is meant to serve a distinct purpose. We have the "Player" type to represent the user's player character, the "Voxel" type to represent the room's voxels, and so on.

### What We are Lacking

While this type-based system is flexible enough to handle a variety of game mechanics, it turns out to be not so scalable when it comes to introducing a huge variety of objects which look different but share roughly the same functionality.

Suppose, for example, that we need to implement objects of type "lamp", whose main function is to lit the surroundings with a source of light. The main issue is that there could be many distinct types of lamp, due to the differences in:

1. Whether the lamp is attached to the ceiling, attached to the wall, attached to the floor, or standing on some other object (see @docs/geometry/wall_attached_object.md ), or
2. The sizes of the lamp's collider (hitbox) in physical space (see @docs/geometry/physics.md ), or
3. The visual appearance of the lamp (i.e. the way in which its mesh instances are composed - see @docs/graphics/instanced_mesh_composition.md ).

If our plan is to have only up to several types of lamp, it may be okay to just implement them as separate object types (i.e. separate entries in `ObjectTypeConfigMap`). Such an assumption, however, greatly limits the future expandability of our game's content. Who knows? We might end up deciding to have hundreds of lamp-variants in the future, each of which slightly differs in visuals, physical properties, and so forth. It will be way too syntactically redundant and memory-heavy to explicitly define them all as literal `ObjectTypeConfig`s.

### What We Already Have

Fortunately, we already do have a way of handling a wide variety of visual differences in a single type of object. The player customization system (see @docs/geometry/player_customization.md ), for instance, lets us give distinct appearances to player objects by means of `ObjectMetadata`.

### What We Need to Implement

The aforementioned player customization system as well as the system of `ObjectMetadata` and `InstancedMeshComposition` upon which it is based, however, are not so sufficient as to effectively handles all potential variations of a single object type. For instance:

1. While it is already possible to give a unique appearance to an object by encoding its `InstancedMeshComposition` data as part of the object's metadata, the encoded bytes themselves can add up to the overall memory size of `RoomRuntimeMemory` quite heavily if we have a huge number of objects whose appearances are all encoded by means of, say, `DefaultCompositionCodec`. We need a much more efficient way of encoding an object's instanced meshes.
2. Right now, each type of object is only capable of having a hitbox of a constant size. This will need to change because of two reasons. First, we may eventually need to let objects change their hitbox sizes in real time (during the game), due to special game mechanics which somehow make them expand, shrink, or distort their own forms in some way. Second, we may need to have numerous size-variants of the same object type, such as beds which come with different sizes (i.e. twin, full, queen, king, etc).

The kind of attachment (e.g. wall-attached, ceiling-attached, etc) probably won't need to be considered as a variation within the same object type, since there will be only up to several kinds of attachment and each of them requires the object to behave in a distinct way, in terms of placement, movement, and so on. For lamps, for example, it is probably okay to have separate object types called "WallLamp", "StandaloneLamp", "CeilingLamp", etc.

## Solution

### Indexed InstancedMeshComposition

As you can see, the most versatile codec for instanced mesh composition is `DefaultCompositionCodec`, which can be used to express pretty much any complex 3D form. The major downside of using `DefaultCompositionCodec`, though, is that it requires quite a long sequence of bytes to encode such a form.

If we build a custom codec (like `PlayerCompositionCodec` or `DoorCompositionCodec`), on the other hand, we may reduce the cost in memory space but will end up facing limitations in terms of the variety of 3D forms that the codec is capable of encoding.

We may decide to build a number of different codecs, as well as a sufficient number of composition builders (i.e. subclasses of `InstancedMeshCompositionBuilder`), to increase our degree of freedom. But then, even if we manage to express a vast collection of 3D forms this way and also manage to scale it to a satisfactory level, such an approach is likely to end up bloating the size of the client app's bundle (due to the enormous amount of the hard-coded logic).

Therefore, I want to suggest that we ought to introduce a two-layer system to `InstancedMeshComposition`'s encoding scheme.

#### Indexing and Pre-Encoding

Just like how `objectTypeIndex` lets us refer to each distinct type of object without specifying the full content of its `ObjectTypeConfig`, we can introduce a new concept called `compositionIndex` and use it as a reference to each predefined way of composing instanced meshes (which is functionally equivalent to each unique implementation of the `InstancedMeshCompositionBuilder.run()` method). Each of these predefined ways, for the sake of minimizing the client app's bundle size, will need to be implemented not as a hard-coded method body, but as a pre-encoded string of base-94 characters.

For this purpose, we will do the following things:

- In @src/server/ssg/ssg.ts , you will see that the `(...)ImageMap.ts` scripts in `src/shared/graphics/image/maps` are being auto-generated during compilation time via `ImageMapBuilder`. The idea is that we can do a similar thing to auto-generate a `.ts`-based cache file of all pre-encoded `InstancedMeshComposition` metadata strings, each of which will then be referenced by a simple index value. This cache file can be formatted in the following manner:
```typescript
const PreEncodedCompositionStringMap = [
    "...", // `InstancedMeshComposition` metadata string at (compositionIndex = 0)
    "...", // `InstancedMeshComposition` metadata string at (compositionIndex = 1)
    "...", // `InstancedMeshComposition` metadata string at (compositionIndex = 2)
    //...
];
```
I manually created a placeholder file for this at `src/shared/graphics/mesh/composition/maps/preEncodedCompositionStringMap.ts` (just for reference), but the SSG module will be the one re-generating this file with the updated list of strings whenever there is a change detected.

- Okay, so the question is, "From which source should the SSG module be constructing 'PreEncodedCompositionStringMap'?" And the answer is, we need to come up with a JSON file as well as a shared protocol (format) through which we pre-encode a bunch of composition rules. For this purpose, I added a new file at `public/app/assets/instanced_mesh_composition/pre_encoding_source.json`. This is basically the "source file" which will be parsed by a new SSG module called `PreEncodedCompositionBuilder`. For now, this JSON file will simply have just one entry (for the existing lamp object's composition rule), but we will be adding more and more entries in the future (not for now). The general parsing rule is simple; first, `PreEncodedCompositionBuilder` can just look up the entry's `codecType` and delegate the appropraite parsing operation to one of the appropriate methods, each of which is designed to parse each specific type of codec (For now, let's have just one parser, designed to handle the "Default" `codecType`). The rest of the entry's data fields, then, can be used to construct the appropriate parameters and `InstancedMeshCompositionPart`s, which will then be fed into the codec's `encode` method to generate the `InstancedMeshComposition` metadata string. This string, together with the codec's type and version bytes (i.e. base-94 characters) will be pushed to `PreEncodedCompositionStringMap` (This is basically the "pre-encoded metadata" I talked about). This pattern can repeat for all the entris in the source JSON file; by the end of the loop, we will have the full array of pre-encoded strings ready, and will then be written to `src/shared/graphics/mesh/composition/maps/preEncodedCompositionStringMap.ts`.

- Note, though, that the source JSON file (`public/app/assets/instanced_mesh_composition/pre_encoding_source.json`) may have data fields with invalid values (e.g. `-1`). This is an indication that such fields are "indeterminate" - that is, they are to be determined and dynamically applied to the corresponding `InstancedMeshCompositionPart`s based upon the `GameObject`'s other state indicators, such as other metadata entries. The color of the lamp object's emissive surface is a good example of this; we simply cannot predefine the exact color of the lamp within a static source file, and so the lamp itself must decide (based on its other metadata entry called `LightProperties`) in what manner it needs to override some of the attributes of its  `InstancedMeshCompositionPart`s.

- I also added a new entry in `InstancedMeshCompositionCodecType` called "Index", as well as its corresponding codec file at `src/shared/graphics/mesh/composition/types/compositionCodec/indexedCompositionCodec.ts`. `IndexedCompositionCodec` will be the one responsible for decoding the object's `compositionIndex` from its `InstancedMeshComposition` metadata string, looking up the "real" `InstancedMeshComposition` metadata string from `compositionIndex`, and then proceeding to delegate the rest of the decoding process to the codec whose `codecType` is the one corresponding to this "real" `InstancedMeshComposition` metadata string's first base-94 character. This way, `IndexedCompositionCodec` will be able to work as some kind of router whose job is to fetch the appropriate pre-encoded composition data and then pass it over to the appropriate codec.

### Variable Collider Dimensions

NOTE: I originally planned to implement a system to handle variable collider dimensions in this plan, but after a bit of research, I realized that it is far trickier than I initially thought (The physics system computes collider dimensions based upon `objectTypeIndex` only; in order for the object's collider to change its shape based on its own metadata (such as the composition index), we will need to change the way the parameters are being passed in, and so forth). If you can think of a way to overcome this difficulty, I will really appreciate it. Otherwise, let's skip the collider part for now, and focus solely on the indexed & pre-encoded `InstancedMeshComposition` system.

### What Happens to the Existing Object Types

- The object type called "Lamp" will be renamed to "WallLamp", since it is a wall-attached lamp object (In the future, we may be adding new object types such as "StandaloneLamp" or "CeilingLamp"). Since the "Lamp" object's `InstancedMeshComposition` only generates its default composition via `generateDefaultParts` (see @src/shared/object/types/objectTypeConfig/lampObjectTypeConfig.ts ), I think each existing lamp object doesn't yet have its own `InstancedMeshComposition` metadata entry (which means lamps that are already installed inside the production (staging) server's rooms won't need any special version migration. If I'm wrong, please tell me). All we will need to do is change the `codecType` of the lamp object in its `ObjectTypeConfig` from "Default" to "Indexed", and make its `generateDefaultParts` simply invoke `IndexedCompositionCodec`'s `decode` method with the `compositionIndex` value of 0 (= default wall-lamp composition index). This will probably let us apply our new indexed-composition system to the game without breaking any existing data.
