# My Initial Plan

## Generic Object Attachment Logic

The wall-attached object placement logic ( @docs/geometry/wall_attached_object.md ) is pretty much obsolete.

Recently, we removed `ObjectSelection`'s clickable world-space arrows and simply made it movable by dragging the selection rect ( @src/client/graphics/types/gizmo/wallAttachmentEditGizmos.ts ). This makes the some of the complex algorithms of `WallAttachedObjectUtil` ( @src/shared/object/util/wallAttachedObjectUtil.ts ), such as `getHorizontalMoveResult` and `getVerticalMoveResult`, obsolete. Such algorithms were invented in order to handle corner-wrapped movements and so on, when either the right-arrow or left-arrow was clicked. Since the arrows are no longer part of the UI/UX, we can now take a much simpler route when it comes to movement calculation. That is, when the user tries to move an object by dragging its selection, why not just raycast toward the pointer's world-space position and try to place the object upon whichever location the ray happens to hit? The attachment logic only needs to make sure that object's surface is parallel to the wall, with the appropriate offsets.

Since this new logic should not solely apply to wall-attached objects but also to floor-attached and ceiling-attached objects (assuming that we are going to implement such objects in the future), we should abandon the concept of "wall-attached objects" altogether and simply come up with a generic attachment logic which encompasses attachments in all directions (-x, +x, -y, +y, -z, +z). That is, there will no longer be "wall-attached objects"; there will only be "attached objects", with configurable constraints. For example, we may consider adding a new field called `attachment?: ObjectAttachmentConfig` to `ObjectTypeConfig`, where:

```typescript
export type ObjectAttachmentConfig = {
    allowedDirections: Vec3[], // Directions in which the object is allowed to be attached (against a voxel quad, such as that of a wall, floor, or ceiling)
};
```

This will let us implement objects which can only be attached to a wall, or objects which can only be attached to a floor, and so on. If we include all 6 possible directions (-x, +x, -y, +y, -z, +z) in `allowedDirections`, it will imply that the object can be attached to any voxel quad.

(Side Note: The introduction of `ObjectAttachmentConfig` may imply that the "wallAttachment" `ColliderType` in `ObjectTypeConfig`'s `ColliderConfig` is now obsolete, and that `ColliderType` now only needs to consist of two choices: "rigidbody" and "nonRigidbody". But I am not sure about this, so please investigate to see if this alternative classification is really appropriate, as well as how much further architectural simplification you will be able to achieve under the current refactoring plan.)

Let us also rename `WallLampGameObject` into `LampGameObject`. Now that the object attachment logic is going to be generic, we will be using just a single object type called "Lamp" to represent not just wall-attached lamps, but also floor-attached and ceiling-attached lamps. When the user drags a lamp on the wall all the way up to the ceiling, the lamp will just attach itself to the ceiling. And when the user drags the lamp all the way down to the floor, it will just attach itself to the floor. But of course, there are some subtleties which need to be resolved here. This brings us to the problem of how the object should be rendered when its direction of attachment changes (See the next section).

## Design of Lamp Object

For now, I am planning to just force `CanvasGameObject` to stay attached to the wall and neither to the floor nor ceiling (Same logic should apply to `DoorGameObject`). However, `LampGameObject` will need to be attachable to surfaces of all directions (wall, floor, ceiling). The problem is that, since `ObjectTransform` has no concept of the roll-angle in the object's direction (It only has a direction vector - not a quaternion), orienting the non-square shape of the lamp's `InstancedMeshComposition` ( @docs/graphics/instanced_mesh_composition.md ) will be awkward. Hence, we are not providing the user with a way of manually rotating an object anyways.

Therefore, let's just make `LampGameObject` scalable (just like `CanvasGameObject`) with the minimum scale of (x: 0.5, y: 0.5, z: 1.0) and the maximum scale of (x: 1.5, y: 1.5, z: 1.0). This will allow the user to simply adjust the shape of the lamp, so as to make it look natural regardless of what the lamp's current orientation is.

The base mesh composition will simply be a unit square (similar to `CanvasGameObject`'s canvas frame mesh instance), and we will no longer be using `IndexedCompositionCodec` for this. Just like a canvas, a lamp needs to be able to have its own frame. Unlike a canvas, however, the user should be able to manually shrink the lamp's whole mesh composition (both the emissive part and the surrounding frame - except the frame's thickness which must solely depend on the mouldingThickness parameter) while keeping the hitbox size the same (The amount of shrinkage will need to be tweakable via a slider with a handful of distinct steps, similar to the one which controls the canvas frame's thickness).

## Findings that change the plan

**1. The side note on `ColliderType`: I'd delete it rather than cut it to "rigidbody" | "nonRigidbody".** Once "wallAttachment" is gone, nothing needs the remaining split:

- The physics engine never reads the type. Collisions run entirely on `applyHardCollisionToOthers` and the soft-force multipliers.
- So "rigidbody" would just repeat the `rigidbody` component declaration, which is why a runtime check has to keep the two in sync.
- Removing `colliderType` from `ColliderConfig` deletes [colliderType.ts](src/shared/physics/types/colliderType.ts) and that check.
- `ColliderConfig` itself stays on attached objects. Their hitbox is still needed for overlap, restricted zones, finding what a block holds up, the selection outline and orbit size, and as the base size for scaling.

**2. Floor and ceiling facings render with an arbitrary spin.** [gameObject.ts:41](src/client/object/types/gameObject.ts#L41) and [:150](src/client/object/types/gameObject.ts#L150) orient objects with `lookAt` and a +y up vector. A facing of ±y is parallel to that up vector, so three.js falls back to a tiny epsilon nudge. A stored facing also decodes slightly off-axis (a 0 component comes back as about -0.0000153), so those tiny x/z parts decide the spin, which could be anything (around 45° for a decoded floor facing). Attached objects therefore need their rotation built from one shared frame (right, up, normal), not from `lookAt`.

**3. Existing lamps would double in height.** Lamps are stored at unit scale on a 1×0.5 base. Your unit-square base makes them 1×1, overlapping neighbours and the ceiling. This needs an `ObjectGroup` version converter (4 → 5) that halves `scale.y` on type index 4.

**4. Two wall-only assumptions break floors and ceilings:**
- [wallAttachedObjectUtil.ts:23-28](src/shared/object/util/wallAttachedObjectUtil.ts#L23-L28) rejects `pos.y <= 0` and `pos.y >= MAX_ROOM_Y`, which is exactly where a ground-floor or top-ceiling object sits. The layers outside the room's range also need to count as solid support.
- [lightSource.ts:68](src/client/object/components/lightSource.ts#L68) puts the light 0.5 along the facing. Along y that is a whole layer, so a floor lamp's light would start one block too high, inside any low overhang, and light nothing.

**5. The lamp is the only pre-encoded composition.** Moving it off `IndexedCompositionCodec` leaves the indexed codec, the pre-encoding step and the thumbnail step with nothing to build. `CompositionThumbnailPanel` already has no importer. No stored lamp holds a composition (only `LightProperties` is ever written), so removing the lamp's entry is safe.

## Design

**`ObjectAttachmentConfig.allowedDirections`**
- It lists the object's allowed facings (the normal of the surface it sits on): the four horizontal ones for Canvas and Door, all six for Lamp.
- It must be enforced in the shared `canPlaceObject`, not only in the drag gizmo, so the server refuses a canvas sent with a +y facing.

**One frame for every facing** (a new `ObjectAttachmentUtil.getFrame(dir)`)
- The facing snaps to its largest component. Today each component is rounded separately, which accepts a diagonal facing as (1,0,1).
- Walls: up = +y and right = up × normal, which is what `lookAt` produces now, so walls render unchanged.
- Floor: up = −z. Ceiling: up = +z.
- The collider, the selection outline, the drag handles, resizing and the rendered rotation all read this frame.
- [physicsColliderStateUtil.ts:66-68](src/shared/physics/util/physicsColliderStateUtil.ts#L66-L68) currently picks the hitbox orientation by comparing x against z, so it misreads ±y facings. Attached objects need their own branch there that uses the frame.

**Snapping to the grid** (the existing rule, extended to all six facings)
- The coordinate along the facing sits on the face plane.
- In-plane x and z snap their centre to the half-voxel grid. That keeps the 1.5-wide door centred on its cell.
- In-plane y (walls only) snaps the bottom edge to the layer grid, as it does now.

**Placement rule** (one version for all six facings, replacing the separate x-facing and z-facing branches)
- Every block in a thin slab just behind the footprint is solid; layers outside the room's range count as solid.
- At least one block in the slab just in front is open.
- The facing is in `allowedDirections`.
- It doesn't overlap another attached object.

**Dragging** (replaces `getMoveResult` and the corner-wrap helpers)
1. On press, record where the pointer grabbed the object, relative to its centre in the frame.
2. On move, add a query to [clientVoxelQueryUtil.ts](src/client/voxel/util/clientVoxelQueryUtil.ts) that finds the first *drawn* face along the pointer ray. It reuses the grid walk of `lineSegmentIsBlockedByDrawnVoxelBlock`, pulled out into a shared walker.
   - Clip the ray to the room first: cells aren't clamped, and the step limit assumes the walk starts inside.
   - "Drawn" means blocks the orbit camera has hidden are passed through, and objects are ignored, so the dragged object never blocks its own ray.
3. If the hit face's facing is allowed, the target is the hit point minus the grab offset. When the facing changed, use the hit point alone, since the offset means nothing on the new surface. If the facing isn't allowed or nothing is hit, intersect the current face plane instead, so a wall-only canvas dragged over the floor keeps sliding along its wall.
4. A new `ObjectAttachmentUtil.findPlacementNear` takes that target if it fits. Otherwise it steps back toward the current position in half-voxel steps, or searches a small neighbourhood when the facing changed, and failing that keeps the current placement. Skip the work when the snapped target hasn't changed.
5. The local preview and the single signal sent on release stay as they are.

**Resizing:** `getResizeResult` works on the frame. The world-y axis holds exactly; horizontal axes may give way by up to a quarter voxel, so on floors and ceilings both axes may (up to four candidates).

**Lamp**
- `scaling`: min (0.5, 0.5, 1), max (1.5, 1.5, 1), step (0.5, 0.5, 0). Your note doesn't give a step; 0.5 keeps footprints on the grid.
- Base hitbox 1×1, plus the converter from finding 3.
- A new `LampCompositionCodec` (codec enum `Lamp: 5`) stores the frame colour, the band-width step (shared with `MouldingCompositionConstants`), the convex and framed flags, and a size step.
- The builder lays out a moulded wood board over the object size × the size factor, with a lit square covering the inside of the band. Clamp the band: at the smallest lamp and size step, two bands are wider than the lamp.
- **Glow colour:** add `deriveParts(obj, parts)` to the `instancedMeshComposer` config, called after every decode. Today the colour is filled in only inside `generateDefaultParts`, which a stored composition bypasses. The lamp fills its lit part's colour from its light there.
- Make `InstancedMeshComposition` an editable key for lamps.
- **UI:** a `CustomizeLampPanel` with the canvas panel's controls plus a size slider. Move the shared frame controls out of [customizeCanvasPanel.tsx](src/client/ui/components/panel/customizeCanvasPanel.tsx) into their own component rather than copying them, and add a frame button to `LampEditOptions`.
