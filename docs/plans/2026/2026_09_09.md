# New Way of Editing the Room

Last Updated: 2026-09-11

## Problem

### Confusing Game Mode Transition

Right now, there is a great sense of ambiguity in the way we transition between the two game modes ("play" and "edit"). One of its root causes is that there are multiple methods through which the user can enter the "edit" mode. That is:

1. The user may enter the "edit" mode by clicking the "editModeButton" in `userRoomIdentity.tsx` (which auto-selects the user's own player object by default), or
2. The user may enter the "edit" mode by first selecting a voxelQuad or GameObject, and then clicking the "startEditingButton" in `gameModeMenu.tsx`.

Exiting the "edit" mode carries its own sense of ambiguity, too, since it is achievable via the following two alternatives:

1. The user may exit the "edit" mode by clicking the "modeExitButton" in `gameModeMenu.tsx`, or
2. The user may exit the "edit" mode by clicking the voxelQuad/GameObject which is already selected (Re-selecting an ongoing selection deactivates it. When nothing is selected, the game mode automatically flips back to "play").

There is also a source of confusion in the way selection works. When the user is in "play" mode and he clicks a voxelQuad or GameObject, a selection gets activated WITHOUT entering the "edit" mode; such a selection, even when activated, preserves the camera's first-person view and lets the user enter the "edit" mode only when he clicks the "startEditingButton" in `gameModeMenu.tsx`.

### Problem with Room Settings

Besides, the current UI flow makes it hard for the admin & room owner to access the room's settings UI (i.e. `configureMyRoomForm.tsx`, `configureHubRoomForm.tsx`); one is able to open it up only by first entering the "edit" mode and then clicking the "configureMyRoomButton" in `gameModeMenu.tsx`. Furthermore, the popup representation of the room's settings UI makes it very difficult for the user to monitor the changes made in the room (in real time) while fiddling with the settings (e.g. lighting parameters, restricted zone coordinates, etc).

## Solution

### General Idea

In order to solve the aforementioned problems, we need to satisfy the following criteria:

1. First of all, there needs to be a strict distinction between the two game modes ("play" and "edit"). And the most straightforward way to ensure this is to create a central "game mode switch" UI element, which will be the only gateway through which the user can transition between the game modes. Whenever the user wants to either enter or exit the "edit" mode, he will be required to flip this switch.
2. The "Room Settings" UI will need to be a horizontally scrollable bottom UI panel (similar to `CustomizePlayerForm`) which the user will be able to turn on/off by means of a toggle-button (see "customizeDoorButton" in `doorEditOptions.tsx`). This will let the user adjust the room's settings and watch their effects immediately, without having to close the popup window.

Let me now explain what needs to be done to achieve this.

### What has already been done

During the recent update (which occurred on 2026-09-10), I made a number of changes to the codebase (committed but not pushed to GitHub yet) which was aimed to reduce the complexity of the world-space selection logic. While doing this, I managed to clean up some of the legacy gameMode-related UI/UX flows mentioned above. So, please keep in mind that some of the problems I have mentioned are already fixed, such as:
  - The problem of the current selection deacivating itself when the user clicks it once again.
  - The problem of voxelQuads/objects being selectable even when the user is in "play" mode.
  - ... and so on.

### UI Changes

- We are going to add a new UI component called `gameModeToggleSwitch.tsx` to the top-bar menu.
  - `gameModeToggleSwitch.tsx` is a clickable inline element which displays a toggle switch in the middle, a "Play" text on the left, and an "Edit" text on the right (Feel free to come up with custom text elements with their own styles; you don't have to use the existing `text.tsx` component for this).
  - The toggle switch is a horizontal capsule with a circle in it, whose position is determined by the current gameMode. When the gameMode switches to "play", the circle smoothly moves to the left. When the gameMode switches to "edit", the circle smoothly moves to the right.
  - It may be even better if the "Play" text gets highlighted when the gameMode is set to "play", and the "Edit" text gets highlighted when the gameMode is set to "edit".
  - `gameModeToggleSwitch.tsx` must not have any background. Anything other than the toggle switch and the two text labels must be fully transparent. And for this reason, both the toggle switch and the text labels must have dark borders in order to let themselves be visually distinguishable from the 3D world behind them (similar to how the userName is being rendered with a dark border in `userRoomIdentity.tsx`).
  - `gameModeToggleSwitch.tsx` must be disabled when the `DisableGameModeTransition` FeatureFlag is active.
  - The tutorial gameplay (`tutorialSinglePlayerModeClientConfig.ts`), whenever it prompts the user to start/end the "edit" mode", will need to indicate `gameModeToggleSwitch.tsx` instead of the now obsolete buttons.

- `cameraZoomSlider.tsx` will no longer occupy the top bar (because there won't be enough space for it). Instead, we will orient it vertically, get rid of the box-shaped background panel, and put it near the rightmost edge of the screen (with a tiny margin on the right). The whole thing must be narrow enough to ensure that it won't interfere with the user's view of the 3D world during the "edit" mode (even on a portrait-mode mobile screen). And yes, `cameraZoomSlider.tsx` will need to be displayed only during the "edit" mode (i.e. when the camera is in orbit-mode) and not during the "play" mode (i.e. when the camera is in firstPerson-mode).

- Let's replace `configureMyRoomForm.tsx` and `configureHubRoomForm.tsx` with a new horizontally scrollable bottom-bar UI component called `customizeRoomForm.tsx` (use `customizePlayerForm.tsx` as a reference). This new bottom-bar UI component will need to have an "X" button (which closes `customizeRoomForm.tsx` when clicked). Make sure that the following sub-panels are contained within the main horizontally scrollable panel:
  - "Texture Pack" (Instead of displaying the whole texture pack preview image right up front, let us just have some kind of "magnifying glass" IconButton which, when clicked, will highlight itself (in a toggle-button manner) and bring up an extra panel right above it which contains the texture pack preview image and the option to change it - in a way similar to how the "customizeDoorButton" in `doorEditOptions.tsx` works).
  - "Restricted Zones" (Instead of displaying the whole `restrictedZoneGrid.tsx` right up front, let us just have some kind of "magnifying glass" IconButton which, when clicked, will highlight itself (in a toggle-button manner) and bring up an extra panel right above it which contains `restrictedZoneGrid.tsx` and the associated "+"/"trash" IconButtons - in a way similar to how the "customizeDoorButton" in `doorEditOptions.tsx` works).
  - "Ambient Light"
  - "Head Light"
  - "Fog"
  - "Smoke"
  - "Clouds"
  - "Ground"

- Let's replace `userRoomIdentity.tsx` and `gameModeMenu.tsx` with a new unified top-bar UI component called `topBarMenu.tsx`.
  - Regardless of the gameMode, `topBarMenu.tsx` must display the `gameModeToggleSwtich.tsx` component and the "exitAppButton" right next to it (These two components are both right-aligned).
  - Let's not display either the userName or the "editModeButton" on `topBarMenu.tsx`.
  - If the user is a "superuser" (i.e. `RoomValidationUtil.isRoomSuperuser(...)` returns `true`), `topBarMenu.tsx` will also need to show a toggle-button called "roomSettingsButton" (placed between `gameModeToggleSwtich.tsx` and the "exitAppButton"), which is a "GearIcon" IconButton that gets highlighted while `customizeRoomForm.tsx` is open (active), and gets un-highlighted when `customizeRoomForm.tsx` closes. Clicking this button will open/close `customizeRoomForm.tsx` (similar to how the "customizeDoorButton" in `doorEditOptions.tsx` works). Also, to simplify the UI logic, let's not try to hide other existing bottom UI components while `customizeRoomForm.tsx` is being displayed (unless implementing such a conditional logic is straightforward and is not going to complicate the code); you only need to make sure that `customizeRoomForm.tsx` is not going to be rendered behind any other component.
  - `topBarMenu.tsx`'s background should be a color gradation which starts as a fully opaque black at the top of the bar and ends up being fully transparent at the bottom of the bar.

### GameMode and Selection Rules

- When the gameMode changes to "edit", the user's own player object needs to be selected initially.
- Clicking an already selected voxelQuad/GameObject must not unselect it.
- During the "edit" mode, the game must always keep exactly 1 active selection (By "selection", I mean either `VoxelQuadSelection` or `ObjectSelection`; see `worldSpaceSelectionUtil.ts` for more details).
- When the user exits the "edit" mode by flipping `gameModeToggleSwitch.tsx` back to "play" (or by pressing the "Escape" key or the "Back" button, or by taking any equivalent action), the current selection will be unselected and there will be no active selection anymore.
- Nothing should be selectable during the "play" mode.
- Clicking any voxelQuad or selectable object should select it (and deactivate the previous selection) during the "edit" mode.
- Whenever the `DisableGameModeTransition` FeatureFlag is active, gameMode must not be able to change.
- Changing the gameMode from "play" to "edit" can be done only by:
  - Flipping `gameModeToggleSwitch.tsx` to "edit".
- Changing the gameMode from "edit" to "play" can be done only by:
  - Flipping `gameModeToggleSwitch.tsx` to "play", or
  - Pressing the "Escape" key while no popup or closable panel is open, or
  - Pressing the "Back" button (or by taking any equivalent action) on the mobile device while no popup or closable panel is open.

### Additional Notes

- `RoomValidationUtil.canUserEditRoom` is now obsolete. From now on, users should be able to edit other peoples' `Regular`-type rooms.
- The aforementioned horizontally-scrollable panel UI components, activated via toggle-buttons, should probably be all based upon a single generic UI component type for a better sense of modularity and abstraction (similar to `form.tsx`). Each of them should probably have an option to display the panel either above the toggle-button from which they originated (in case of the restricted-zones editing, texture-pack editing, or door-color editing, etc), or at some absolute offset with respect to the screen (in case of `CustomizePlayerForm` and `CustomizeRoomForm`, etc). Also, these panels should close themselves not only when their "X" buttons or their respective toggle buttons get clicked, but also when the "Escape" key or the "Back" button gets pressed (similar to how the topmost popup form gets closed when the "Escape" key or the "Back" button gets pressed).
