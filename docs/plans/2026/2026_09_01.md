# Custom Lights

Last Updated: 2026-09-03

## Step 1: My Preliminary Conversation with Claude

### My Question

Right now, there is only one point light in our app's three.js scene. If you take a look at `graphicsManager.ts`, you will see that its `load` method is attaching a `THREE.PointLight` to the main camera. This is essentially the "flashlight" that the player carries on his head, so that objects that are closer to the player tend to appear brighter (which is intuitively sound, and tends to produce a natural fadeout effect, which is good from a cognitive perspective).

The problem with the single-light approach, however, is that the rest of the room (anywhere that is not sufficiently in vicinity of the player) stays too dark. The result of this is that so many opportunities in terms of spectacular lighting effects are lost in this kind of setting. With only one point light (which is attached to the camera), the whole room feels like a cave.

Therefore, I am thinking of letting players install multiple point lights in the room (with custom colors, light intensities, and so forth), so as to let them experiment with various sorts of composition among different sources of light. This will be a great way of facilitating the players' creative freedom.

One major concern I have in regard to this, though, is that the performance drop can be quite serious if we happen to have too many point lights inside the room. So I am considering the following ways of reducing the GPU's computational cost:

1. Add a thick fog to the scene, so that the app won't need to render the sources of light and their reflections which are far away from the camera.
2. Limit the total number of point lights which can be installed inside the room (Forcing point lights to keep some minimum distances from each other might be an even better solution, but I am not sure how to design the UI/UX in a way which is intuitive enough to help the user understand this concept).
3. Render fragments using vertex-lighting instead of pixel-lighting.
4. Let voxelQuads and static GameObjects (those which do not move) have their surfaces re-baked by nearby sources of light (i.e. runtime light-mapping), each time a nearby source of light gets displaced. (Note: I am afraid that this solution might complicate the code too much, due to the complexity of its logic)

What's your thought on this? Which approach shall I take, in order to let us have multiple sources of light inside the room (for richer visual experience) without hurting the GPU's performance too much?

### Claude's Answer

I read the scene setup, all the material constructors, and the three.js internals to check what a second light actually costs here. There's a constraint that changes the shape of the answer, so let me start there.

#### The thing that decides this: three.js's forward renderer

Two facts from `node_modules/three` (r180, per package.json):

**Every lit fragment evaluates every point light, unconditionally.** `light.distance` does not cull anything — the loop still runs and `getDistanceAttenuation` just returns 0. A lamp across the room costs exactly what a lamp at your feet costs.

**The light count is compiled into the shader.** `numPointLights` is a `#define` and part of the program cache key (`WebGLPrograms.js:320` and `:452`, applied at `WebGLProgram.js:242`). Add or remove one light and *every material in the scene recompiles* — including the wood shader, which is several hundred lines of noise with a 3×3 knot loop in the fragment stage. That cost is currently paid deliberately during the loading screen via the shader-precompilation step in @src/client/graphics/graphicsManager.ts . A player placing a lamp would pay it mid-frame instead.

And a third, which is a visual problem rather than a perf one: **nothing in the codebase calls `castShadow` or `receiveShadow`.** `shadowMap.enabled = true` in @src/client/graphics/graphicsManager.ts is currently dead weight. Real point lights would shine straight through walls. In a 32×32×16 grid where players build enclosures, a lamp glowing through a solid wall from the next room over looks more broken than the cave does. Fixing that with real lights means point-light shadow maps — cube maps, six passes per light — which is not on the table at any count above about one.

#### The four options

**1. Thick fog — do it, but it is not an optimization.** In a forward renderer the fragment evaluates all the lights and *then* mixes toward the fog color. It saves nothing. Its real value is atmosphere and depth cueing, and it's cheap, so keep it — just don't count it as one of the performance measures. Pulling the far plane in would save geometry, but it's already at roughly the room diagonal, so there's little there.

**2. A cap — necessary if we use real lights, but it caps the feature, not the cost.** On the minimum-distance idea: drop it. It couldn't be explained intuitively because it isn't true — two lights crammed in one corner cost precisely what two lights across the room cost. The difficulty in designing that UI was the design correctly refusing to express a rule that buys nothing.

**3. Vertex lighting — not available the way it's imagined here, and wrong for this geometry.** As of r180 `MeshLambertMaterial` is per-fragment too (`lights_fragment_begin` sits in its fragment stage, `meshlambert.glsl.js:107`). We'd be hand-writing a Gouraud path. And a voxel face is a 4-vertex quad, so light would be sampled at the corners only — a lamp near the middle of a wall would produce almost nothing. It would also delete the tin sheen and the wood moulding relief, both of which are fragment-stage work.

**4. Runtime light-mapping — right instinct, wrong granularity.** The worry about complexity is justified for a real lightmap (UV atlas over every visible quad in the room, invalidated by every voxel edit and by every other player's edit). But there's a much simpler version of the same idea, and it's simpler *because the room is already a grid*.

#### Recommendation: a voxel light grid, plus keep the head lamp

Treat player lights as data rather than as `THREE.PointLight` objects.

- The room is a fixed 32×32×16 cell volume (see the voxel grid constants in @src/shared/system/sharedConstants.ts ) — 16,384 cells. When a light is placed, moved, or recolored, flood-fill RGB light outward through the *open* cells, attenuating per step and stopping at solid voxels. That's a sub-millisecond BFS, run only when a light changes, never per frame.
- Upload the result as a `Data3DTexture` — 32×32×16 RGB is 48 KB, nothing.
- Every material already goes through `onBeforeCompile` (see @src/client/graphics/maps/materialConstructorMap.ts ), so inject one shared chunk that samples that texture at the fragment's world position and adds it to the lighting. **One texture fetch per fragment, constant cost whether the room holds 3 lights or 300.** Linear filtering interpolates between cells for free.

What that gets us:

- **O(1) GPU cost in the number of lights**, so the cap becomes a design choice rather than a frame-rate cliff.
- **No shader recompiles ever**, because `NUM_POINT_LIGHTS` stays at 1 forever.
- **Walls occlude light for free**, because the flood fill respects solid voxels — the thing real point lights cannot give us without cube-map shadows.
- **Moving things are lit too.** Other players, thrown objects, and doors sample the volume at their own position. A baked lightmap would leave them out; this doesn't.
- The camera lamp stays a real `THREE.PointLight`. It's the one light that genuinely moves every frame, and we want true per-pixel falloff for that near-field cue.

The honest trade-off: the grid is diffuse-only, so player lamps produce no specular glint. Cell resolution is 1×0.5×1 world units, so illumination is soft and slightly blocky up close — which with trilinear filtering reads as bounced ambient, and is more or less exactly the "the room is not a cave" effect we're after. Diffuse-only is arguably actively good here, because the tin and wood shaders are explicitly written around the degeneracy of a single head-mounted lamp (see the specular-falloff comments in @src/client/graphics/maps/materialConstructorMap.ts ); a second real specular light would change how both of those read, and not for the better.

#### Prototyping the art direction first

We can validate whether multiple lights even look good before building any of this: pre-create a fixed handful of `THREE.PointLight`s at startup with intensity 0, and have "placing a light" just move one and turn it up. `NUM_POINT_LIGHTS` never changes, so no recompile storm. Four or so is safe to test with. The through-wall bleeding shows up immediately, which is the fastest way to confirm the grid is the right destination.

#### One thing to decide early

Whether a light is a placeable `GameObject` or room-level state. An object is the better fit — it reuses placement, permissions, and networking, and per CLAUDE.md a new kind of placeable object owes room generation nothing. But the **fog color and density, and the ambient level, are room-level parameters**, so those do need `RoomGenerationUtil`, both procedural builders, and every `SinglePlayerModeConfig` extended in the same change — and they need to agree with the room's texture pack palette.

## Step 2: Structural Planning (written by Claude, after additional discussions)

### Decisions Carried Forward

Settled during Step 1 and the drafting that followed:

1. **Player-installed lights are data, not `THREE.PointLight` objects.** The scene keeps exactly one real point light — the head lamp on the camera — forever. `NUM_POINT_LIGHTS` never changes, so no material ever recompiles because of a lamp.
2. **The room's own voxel grid is the light volume.** A "voxel block" is one collision layer of one voxel, and light is propagated block to block. Nothing new has to be built to describe where light can and cannot go: `Voxel.collisionLayerMask` already says it.
3. **Propagation carries distance travelled, not brightness remaining.** Brightness is evaluated at the end from the same windowed inverse-power curve three.js applies to a real point light, so a lamp and the head lamp are tuned in the same units.
4. **One bounded breadth-first fill per light**, accumulated into a shared buffer. The light's range bounds the search, so cost scales with a lamp's range rather than with the size of the room, and the whole room is recomputed from scratch whenever anything changes rather than being updated incrementally.
5. **The result is a `Data3DTexture` sampled once per fragment.** The GPU cost is O(1) in the number of lights.
6. **Walls occlude light for free**, because the fill stops at solid blocks. This is the thing real point lights could not have given us without cube-map shadow passes.
7. **Client-side only.** The lights themselves are replicated GameObjects; the block map derived from them is a rendering detail every client computes locally. The server never computes or sends it. (This would have to move to `/shared` if light ever became gameplay-relevant — a stealth or dark-room mechanic.)
8. **The block map lives in `GraphicsManager`**, alongside the scene and camera, and is kept for the app's whole lifetime rather than rebuilt per room.
9. **Diffuse-only, no directionality.** A lamp casts no specular glint. This is a limitation and also a convenience, since the tin and wood shaders are written around the degeneracy of a single head-mounted lamp.

    // Voxel blocks
    //
    // A "voxel block" is one collision layer of one voxel — the smallest volume the grid
    // distinguishes, and the unit light is propagated through. The collision layer varies fastest
    // in the index, then the column, then the row, so that a voxel's own layers are contiguous and
    // walking a column costs one stride.
    //-------------------------------------------------------------------------------------

    getVoxelBlockIndex(row: number, col: number, collisionLayer: number): number
    {
        return (row * NUM_VOXEL_COLS + col) * NUM_COLLISION_LAYERS + collisionLayer;
    },

    {
        return (voxelBlockIndex / (NUM_VOXEL_COLS * NUM_COLLISION_LAYERS)) | 0;

    {
        return ((voxelBlockIndex / NUM_COLLISION_LAYERS) | 0) % NUM_VOXEL_COLS;

    {
        return voxelBlockIndex % NUM_COLLISION_LAYERS;

import * as THREE from "three";
import Voxel from "../../../../shared/voxel/types/voxel";
import VoxelQueryUtil from "../../../../shared/voxel/util/voxelQueryUtil";
import Vec3 from "../../../../shared/math/types/vec3";
import { NUM_COLLISION_LAYERS, NUM_VOXEL_BLOCKS, NUM_VOXEL_COLS, NUM_VOXEL_ROWS }
    from "../../../../shared/system/sharedConstants";
import { LIGHT_BLOCK_MAP_MAX_BRIGHTNESS, VOXEL_BLOCK_NEIGHBOR_OFFSETS }
    from "../../../system/clientConstants";
import LightSource from "./lightSource";

export default class LightBlockMap
{
    // Scratch buffers, allocated once and reused by every recomputation. Propagation runs whenever a
    // lamp is dragged, so allocating buffers of this size per run would hand the garbage collector a
    // steady stream of work in the middle of gameplay.
    private distanceFromLightByBlockIndex = new Float32Array(NUM_VOXEL_BLOCKS);
    // A block is enqueued at most once per light source, because every step through the grid costs
    // the same and so the first time a block is reached is also the cheapest (see accumulateLightSource).
    // That invariant is what bounds this queue; it is checked rather than assumed, since writing past
    // the end of a typed array is silently dropped rather than throwing.
    private pendingBlockIndicesQueue = new Int32Array(NUM_VOXEL_BLOCKS);
    private reachedBlockIndices = new Int32Array(NUM_VOXEL_BLOCKS);

    // Three entries per block. Light is accumulated here rather than into the texture's own storage
    // because what accumulates has no upper bound, while the texture holds bytes — so the two are
    // separated by the exposure step in uploadBlockColors.
    private blockLightBuffer = new Float32Array(NUM_VOXEL_BLOCKS * 3);

    // Four entries per block. Bytes rather than floats because a float texture is only filterable
    // where OES_texture_float_linear is available, which excludes a good deal of mobile — and a
    // light map that silently samples black on those devices is a far worse failure than the
    // precision that is given up here. Four channels rather than three because three.js derives no
    // sized internal format for an RGB float/byte 3D texture, so RGB is not a usable combination;
    // the alpha channel is written once in the constructor and then ignored.
    private blockColorBuffer: Uint8Array;
    private blockColorTexture: THREE.Data3DTexture;

    private lightSourceByObjectId: { [objectId: string]: LightSource } = {};

    // The voxels light is propagated through. Held rather than looked up so that this class does not
    // have to reach back into App for the current room, which would close an import cycle
    // (app -> graphicsManager -> lightBlockMap -> app).
    private voxels: Voxel[] | undefined;

    // Set whenever anything propagation depends on changes, and consumed once per frame, so that
    // dragging a lamp across the room costs one recomputation per frame rather than one per
    // transform update.
    private needsRecomputation = true;

    constructor()
    {
        this.blockColorBuffer = new Uint8Array(NUM_VOXEL_BLOCKS * 4);
        for (let blockIndex = 0; blockIndex < NUM_VOXEL_BLOCKS; ++blockIndex)
            this.blockColorBuffer[blockIndex * 4 + 3] = 255;

        // The dimensions follow the index layout rather than the world's axis order: a Data3DTexture
        // reads its data with the first dimension varying fastest, and the fastest-varying part of a
        // voxel-block index is the collision layer. So the texture's axes are (collision layer, col,
        // row), and a shader sampling it has to swizzle a world position into that order.
        this.blockColorTexture = new THREE.Data3DTexture(
            this.blockColorBuffer, NUM_COLLISION_LAYERS, NUM_VOXEL_COLS, NUM_VOXEL_ROWS);
        this.blockColorTexture.format = THREE.RGBAFormat;
        this.blockColorTexture.type = THREE.UnsignedByteType;
        // Interpolating between blocks is what turns a grid of cells into a smooth wash of light.
        // Data3DTexture defaults both filters to NearestFilter, so both have to be set.
        this.blockColorTexture.minFilter = THREE.LinearFilter;
        this.blockColorTexture.magFilter = THREE.LinearFilter;
        // Left at its default (no color space): the buffer holds linear-space light, and marking it
        // as sRGB would have three.js convert it a second time on the way into the shader.
    }

    getDataTexture(): THREE.Data3DTexture
    {
        return this.blockColorTexture;
    }

    requestRecomputation()
    {
        this.needsRecomputation = true;
    }

    // Called when a room is loaded, and with no voxels when one is unloaded. This object outlives
    // every room it is used for (GraphicsManager keeps it for the app's whole lifetime), so the
    // previous room's lamps have to be dropped explicitly or they would go on lighting the next one.
    resetForRoom(voxels: Voxel[] | undefined)
    {
        this.voxels = voxels;
        this.lightSourceByObjectId = {};
        this.needsRecomputation = true;
    }

    addLightSource(objectId: string, lightSource: LightSource) { /* ... requestRecomputation() */ }
    removeLightSource(objectId: string) { /* ... requestRecomputation() */ }
    setLightSourcePosition(objectId: string, worldPos: Vec3) { /* ... requestRecomputation() */ }

    update()
    {
        if (this.needsRecomputation && this.voxels != undefined)
        {
            this.needsRecomputation = false;
            this.blockLightBuffer.fill(0);
            for (const objectId in this.lightSourceByObjectId)
                this.accumulateLightSource(this.voxels, this.lightSourceByObjectId[objectId]);
            this.uploadBlockColors();
        }
    }

    // Spreads one light source through the open blocks around it, and adds what arrives at each of
    // them into the accumulation buffer.
    //
    // The search is a breadth-first flood fill that carries the distance travelled rather than the
    // brightness remaining, so that the brightness can be evaluated at the end from the same curve
    // three.js applies to a real point light. Light that bends around a corner therefore keeps
    // falling off along the bent path, which stands in for the bounce that is not being simulated.
    //
    // Two things keep it cheap. The light's own range bounds the search, so a small lamp costs a
    // small ball of blocks rather than a sweep of the room; and because every step through the grid
    // costs the same, breadth-first order reaches each block by its cheapest route first, so no
    // block is ever visited twice.
    private accumulateLightSource(voxels: Voxel[], lightSource: LightSource)
    {
        const startRow = VoxelQueryUtil.getVoxelRowFromWorldZ(lightSource.worldPos.z);
        const startCol = VoxelQueryUtil.getVoxelColFromWorldX(lightSource.worldPos.x);
        const startCollisionLayer =
            VoxelQueryUtil.getVoxelCollisionLayerFromWorldY(lightSource.worldPos.y);
        if (!VoxelQueryUtil.isVoxelBlockWithinBound(startRow, startCol, startCollisionLayer))
            return;
        // A lamp buried inside a block lights nothing. Worth passing over quietly rather than
        // treating as an error, since a lamp ends up inside a block whenever somebody builds over it.
        if (VoxelQueryUtil.isVoxelBlockOccupied(voxels, startRow, startCol, startCollisionLayer))
            return;

        const startBlockIndex =
            VoxelQueryUtil.getVoxelBlockIndex(startRow, startCol, startCollisionLayer);

        this.distanceFromLightByBlockIndex.fill(Number.POSITIVE_INFINITY);
        this.distanceFromLightByBlockIndex[startBlockIndex] = 0;

        let queueHead = 0;
        let queueTail = 0;
        this.pendingBlockIndicesQueue[queueTail++] = startBlockIndex;

        let numReachedBlockIndices = 0;
        this.reachedBlockIndices[numReachedBlockIndices++] = startBlockIndex;

        while (queueHead < queueTail)
        {
            const blockIndex = this.pendingBlockIndicesQueue[queueHead++];
            const distanceToBlock = this.distanceFromLightByBlockIndex[blockIndex];
            const row = VoxelQueryUtil.getVoxelBlockRow(blockIndex);
            const col = VoxelQueryUtil.getVoxelBlockCol(blockIndex);
            const collisionLayer = VoxelQueryUtil.getVoxelBlockCollisionLayer(blockIndex);

            for (const offset of VOXEL_BLOCK_NEIGHBOR_OFFSETS)
            {
                const neighborRow = row + offset.rowOffset;
                const neighborCol = col + offset.colOffset;
                const neighborCollisionLayer = collisionLayer + offset.collisionLayerOffset;
                if (!VoxelQueryUtil.isVoxelBlockWithinBound(
                    neighborRow, neighborCol, neighborCollisionLayer))
                    continue;
                // Light stops at a solid block rather than passing through it. This is what gives
                // walls their shadows without any of the cost of shadow mapping.
                if (VoxelQueryUtil.isVoxelBlockOccupied(
                    voxels, neighborRow, neighborCol, neighborCollisionLayer))
                    continue;

                const distanceToNeighbor = distanceToBlock + offset.worldDistance;
                if (distanceToNeighbor >= lightSource.range)
                    continue;

                const neighborBlockIndex = VoxelQueryUtil.getVoxelBlockIndex(
                    neighborRow, neighborCol, neighborCollisionLayer);
                // Compared against the distance already recorded rather than against a "visited"
                // flag. The two are equivalent while every step costs the same, and only this form
                // stays correct if that ever stops being true — an unevenly sized neighbourhood, or
                // blocks that dim light instead of stopping it, both make a later arrival able to
                // beat an earlier one.
                if (distanceToNeighbor >= this.distanceFromLightByBlockIndex[neighborBlockIndex])
                    continue;

                if (queueTail >= NUM_VOXEL_BLOCKS)
                {
                    console.error("Voxel-block queue overflowed while propagating light.");
                    break;
                }
                if (this.distanceFromLightByBlockIndex[neighborBlockIndex] ===
                    Number.POSITIVE_INFINITY)
                    this.reachedBlockIndices[numReachedBlockIndices++] = neighborBlockIndex;
                this.distanceFromLightByBlockIndex[neighborBlockIndex] = distanceToNeighbor;
                this.pendingBlockIndicesQueue[queueTail++] = neighborBlockIndex;
            }
        }

        // Only the blocks this light actually reached are accumulated, so adding a lamp to the room
        // costs time proportional to that lamp's range rather than to the size of the room.
        for (let i = 0; i < numReachedBlockIndices; ++i)
        {
            const blockIndex = this.reachedBlockIndices[i];
            const brightness = getDistanceAttenuation(
                this.distanceFromLightByBlockIndex[blockIndex], lightSource.range, lightSource.decay);
            const lightIndex = blockIndex * 3;
            this.blockLightBuffer[lightIndex    ] += lightSource.colorR * brightness;
            this.blockLightBuffer[lightIndex + 1] += lightSource.colorG * brightness;
            this.blockLightBuffer[lightIndex + 2] += lightSource.colorB * brightness;
        }
    }

    // Exposes the accumulated light through the byte range the texture holds. Clamping is what makes
    // the brightest places around a lamp flatten to white rather than wrap around to black, since a
    // typed array of bytes takes an out-of-range number modulo 256 rather than clamping it.
    private uploadBlockColors()
    {
        const brightnessToByte = 255 / LIGHT_BLOCK_MAP_MAX_BRIGHTNESS;
        for (let blockIndex = 0; blockIndex < NUM_VOXEL_BLOCKS; ++blockIndex)
        {
            const lightIndex = blockIndex * 3;
            const colorIndex = blockIndex * 4;
            this.blockColorBuffer[colorIndex] =
                Math.min(255, this.blockLightBuffer[lightIndex] * brightnessToByte);
            this.blockColorBuffer[colorIndex + 1] =
                Math.min(255, this.blockLightBuffer[lightIndex + 1] * brightnessToByte);
            this.blockColorBuffer[colorIndex + 2] =
                Math.min(255, this.blockLightBuffer[lightIndex + 2] * brightnessToByte);
        }
        this.blockColorTexture.needsUpdate = true;
    }
}

// The same curve three.js applies to a point light (a windowed inverse-power falloff), so that a
// light in the block map and a real THREE.PointLight of the same range and decay read as the same
// thing. A free function rather than a method, since it depends on nothing the class holds.
function getDistanceAttenuation(distanceToLight: number, range: number, decay: number): number
{
    const falloff = 1 / Math.max(Math.pow(distanceToLight, decay), 0.01);
    const rangeRatio = distanceToLight / range;
    const rangeRatioPow4 = rangeRatio * rangeRatio * rangeRatio * rangeRatio;
    const rangeWindow = Math.max(0, Math.min(1, 1 - rangeRatioPow4));
    return falloff * rangeWindow * rangeWindow;
}

### Sampling the Block Map from the Materials

The block map is worthless until something reads it. Every lit material in `MaterialConstructorMap`
is a `MeshPhongMaterial` with an `onBeforeCompile` hook already, so the injection is uniform, and it
should be written once and applied to all of them rather than pasted into each — the six that need
it are `InstancedTexturePack`, `InstancedColor`, `InstancedEye`, `InstancedTin`, `InstancedWood` and
`Texture`. The three `MeshBasicMaterial` ones (`Sprite`, `Wireframe`, `LineBasic`) are unlit and are
left alone.

- **New file** `src/client/graphics/shaders/lightBlockMapGLSL.ts`, alongside `valueNoiseGLSL.ts`,
  holding the sampling function and the uniform declarations.
- **New helper** in `MaterialFactory` (or a small `lightBlockMapMaterialUtil`) that takes a material
  and wires both halves: the vertex stage gains a world-position varying, the fragment stage gains
  the sample.
- The sample is added to `irradiance` at `#include <lights_fragment_maps>`, which is the point where
  three.js already folds a light map's contribution in. Everything downstream — the tin's specular
  compression, the wood's carving shade — then behaves as it does today.
- **The sample point is offset half a block along the surface normal.** Interpolating between a lit
  block inside a room and a dark one outside it makes a one-block-thick wall bleed light onto its
  dark side; pushing the sample off the surface is the standard remedy and costs one addition.
- The uniform is set once per material when the texture is created, not per frame — the texture
  object is stable for the app's lifetime, and only its contents change.

### New GameObject Type: `Lamp`

*(Proposed here, not yet discussed. Everything in this section is a first sketch.)*

A lamp is a placeable object, which per the room-generation rule owes room generation nothing. It
follows `CanvasObjectTypeConfig` closely, because a canvas is the existing example of "a thing a
player hangs on a wall, whose appearance is metadata, capped per room, editable only by those who may
edit the room".

- **`objectTypeIndex: 4`** in `ObjectTypeConfigMap` — appended, never inserted, since the index is
  what gets persisted.
- **`persistent: true`, `autoUnload: true`**, as for a canvas.
- **`MAX_LAMPS_PER_ROOM`** in `sharedConstants.ts`. The GPU cost is flat in the number of lamps, so
  this cap is about propagation time, room clutter, and how much a room's contents cost to send —
  not about frame rate. Something in the region of a few dozen.
- **Permissions**, all mirroring the canvas: `canUserAddObject` checks `canUserEditRoom`, rejects a
  spoofed `sourceUserID`, and enforces the cap; `canUserRemoveObject` checks `canUserEditRoom`;
  `canUserSetObjectTransform` requires `ignorePhysics`; `canUserSetObjectMetadata` accepts only the
  lamp's own keys and validates each against its curated table.
- **Components**: `collider` (`wallAttachment`, a small hitbox), `instancedMeshComposer` for the
  lamp's own body, `orbitOccluder`, and the new `lightSource` component below.

#### Metadata

Two new `ObjectMetadataKey` entries, kept apart for the same reason `Label` and `LabelColor` are:

- **`LightColor`** — a position in a light-color palette, not a free color. Validating an index
  against a table is what keeps a client from installing a lamp the server never agreed to.
- **`LightPower`** — a step index into a curated table of `(range, decay, intensity)` triples, rather
  than three free numbers. One dial is easier to present than three, the values stay within what the
  exposure constant was tuned for, and the propagation cost per lamp is bounded by construction.

#### Curated Data

- **New map** `src/shared/graphics/light/maps/lightPowerMap.ts` — the `LightPower` steps. Shared,
  because the server validates against it.
- **`RoomPaletteMap` gains a light-color palette per texture pack.** A lamp's color has to sit
  against the room's own materials, and the room-generation rule requires curated data to cover every
  option a room can be generated with — which here means every texture pack, not only `default`.

### New GameObjectComponent Types

#### `lightSource` (Phase 1)

The bridge between a GameObject and the block map. Client-side, like every other component.

- **Config**: a `localOffset`. This is not cosmetic. A wall-attached lamp's origin sits on the face
  of a wall, and `accumulateLightSource` returns immediately when the starting block is solid — so a
  lamp whose emitter is not pushed clear of the wall it hangs on lights nothing at all. The offset is
  applied along the object's facing direction.
- **`onSpawn`** builds a `LightSource` from the object's transform and its `LightColor`/`LightPower`
  metadata and calls `addLightSource`.
- **`onDespawn`** calls `removeLightSource`.
- **`onSetMetadata`** rebuilds colour and power when either key changes.
- **`update`** compares the object's current world position against the one last registered and calls
  `setLightSourcePosition` when it has moved. Polling rather than hooking the transform is what makes
  a drag collapse naturally into one recomputation per frame.

#### `lightObstacle` (Phase 4)

Objects large enough to cast a shadow of their own — and, later, thin or tinted ones that dim light
rather than stopping it.

- **Config**: a default transmittance triple, overridable per object by metadata for stained glass.
- Registers the blocks its hitbox overlaps into an occlusion buffer on the block map, and unregisters
  on move — exactly what `PhysicsObject` already does against its intersecting voxels.
- **Needs a Y-aware box rasterizer.** `PhysicsVoxelUtil.getVoxelsInBox` walks only the XZ footprint,
  because physics voxels are columns; the block grid is genuinely 3D. This belongs next to it, as
  `getVoxelBlocksInBox`.
- **This is what breaks the breadth-first guarantee.** Once a block can dim light instead of stopping
  it, a longer route can arrive brighter than a shorter one, and the queue has to allow a block to be
  re-enqueued whenever any channel improves. The comparison in `accumulateLightSource` is already
  written in the form that survives this; what changes is that `pendingBlockIndicesQueue` has to
  become a ring buffer, since a block can then be enqueued more than once.

### Room-Level Parameters: Fog and Ambient

Fog is not a performance measure — in a forward renderer the fragment does all its lighting and
*then* mixes toward the fog colour — but it is most of the atmosphere, and it is what keeps the far
wall of a lit room from looking flat. Unlike a lamp, these are room *parameters*, so the
room-generation rule applies in full and every one of these moves in the same change:

- `Room` — the fields, plus encoding and the `DBRoom` migration for rooms that already exist.
- `RoomGenerationUtil` and both procedural builders — choosing them.
- Every `SinglePlayerModeConfig`, via `RoomBuilderParams` — declaring them.
- `RoomPaletteMap` — fog colour has to agree with the room's palette, for every texture pack.

Worth treating as its own phase, since it touches the server, the database and generation, while
everything above this point is client-only.

### Build Order

1. **The block map and the shader sampling, with a hard-coded lamp.** No object, no UI, no
   persistence. This is the phase that answers whether the whole idea looks good, and it is
   throwaway-cheap if it does not.
2. **The `Lamp` object**: type config, metadata, curated tables, permissions, cap, placement, and the
   `lightSource` component. At the end of this phase the feature is real and shippable.
3. **Fog and ambient as room parameters**, with generation and migration.
4. **`lightObstacle` and partial transmittance**, with the relaxing queue that comes with it.

### Open Questions

- **Wall-mounted only?** `WallAttachedObjectUtil` constrains attachment to vertical faces, so a
  sconce works and a ceiling pendant does not. Standing lamps and hanging lamps would need either a
  new collider type or a different placement flow. Phase 2 can ship wall-mounted alone.
- **Does the head lamp dim in a well-lit room?** Keeping it at full strength in a brightly lamp-lit
  room will wash out exactly the composition the player was arranging. Sampling the block map at the
  camera and easing the head lamp down as the room brightens is one answer, and it is also a way to
  make the lamps feel consequential.
- **Should a lamp's own body read as emissive?** It sits in the brightest block of its own light, so
  it will already come out bright. Whether that is enough for it to look like the source, rather than
  like an object that happens to be well lit, is a question for the first phase.
- **8-bit banding.** If the dark parts of a room band, storing the square root of brightness and
  squaring it in the shader doubles the precision where it is needed, for one multiply.
- **Directionality.** Storing six directional components per block instead of one (an ambient cube)
  would give normal-dependent shading and a sense of which way a lamp lies. It does not change
  propagation at all — only what a block stores and how the shader reads it — so it stays available
  as a later upgrade.
