# Shrinkable Blocks

## Definitions

- The room's voxel grid is made up of a 2D array of voxels.
- Each voxel is made up of a stack of collisionLayers, as well as a "floor" voxel quad and a "ceiling" voxel quad.
- Each collisionLayer can be occupied by a voxel block.
- Each voxel block is made up of up to 6 voxel quads.
- Each voxel quad represents one of the 6 faces of the voxel block's cuboid form.

For more details, see: @docs/geometry/voxel_grid.md

## Problem

Right now, every voxel block is 1x0.5x1 in size (i.e. x: 1, y: 0.5, z: 1). This makes it hard for the user to create something which has the thickness of 0.5 across the XZ plane, such as a thin wall, a fence, a small electronic device such as a radio, a seat back, and so on.

### New Encoding Scheme

The current voxel encoding scheme expresses the state of occupancy of each voxel's blocks by encoding the voxel's collisionLayerMask (16 bits in size), where each of its bits represents whether each of the blocks is (completely) occupied or (completely) empty. Now that we are going to allow each block to partially occupy its volume, we should get rid of the encoding of collisionLayerMask and start leveraging the unused bits of the voxel quads' encoded data.

When you see the bottom comments of @src/shared/voxel/types/voxel.ts , you will find out that 1 of the 8 bits of each voxel quad's encoded data is unused. Since each voxel block's encoded data (aka "6-Byte CollisionLayer Content") consists of 6 voxel quads' encoded data, we can conclude that each voxel block has 6 spare bits which it is free to use for encoding extra bits of information.

Let us represent each of the 10 aforementioned occupancy states as a binary number, and encode each of the bits of this binary number in each of the unused bits of the voxel quads' encoded data.

When the user selects a voxel quad (i.e. `VoxelQuadSelection` gets activated), its world-space selection outline rect should show the "resize handles" (draggable yellow circles), similar to those of @src/client/graphics/types/gizmo/objectAttachmentEditGizmos.ts (Note: Feel free to create a new file called `voxelQuadEditGizmos.ts`. This concludes my demonstration of the concept of "resize" in the context of voxel quad selection. The core of the idea is that we should modify the block's state in the way which will resize the selected voxel quad in the intended direction.

Besides resizing, the user should also be able to move the selected voxel quad's block by dragging its main body (just like how the user can move an object by dragging it). A dragged block's landing spot will be the closest "attachable" location discovered by the latest pointer raycast. Note, though, that casting a single ray may not be appropriate in case of a voxel block's displacement. Some kind of "cuboid-cast" may yield a more intuitive result.
