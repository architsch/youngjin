# Partial Room-Editing Restrictions

Last Updated: 2026-09-04

Note: This plan is a follow-up from the previous admin system implementation work (see @docs/plans/2026/2026_08_29.md ).

## Problem

### Initial Motivation

The admin system now allows `Admin` users to create brand new Hub rooms, add custom doors (`DoorGameObject`) to rooms, and connect rooms to one another by setting the doors' destination metadata. This creates an opportunity to construct a network of rooms, where each pair of connected rooms can be considered as being "adjacent" to each other from a physical standpoint.

The main issue with this imaginary sense of adjacency is that it is likely to cause confusion if the boundary walls of a pair of adjacent rooms, which are supposedly playing the role of a division between these two rooms, happen to have holes (cavities) on them. Since the three.js scene's black background (in this app) is eventually going to be replaced by a skybox, the presence of any hole on the wall will be a direct suggestion that what lies beyond the wall is vast outdoor space. This will directly contradict with the expectation that the other side of the wall should be another indoor space (i.e. room).

In order to prevent this sort of perceptual conflict, some portions of the boundary walls must stay intact and never permit any holes on them. And in order to ensure this, only `Admin` users should be allowed to remove parts of the wall which are supposedly adjacent to the boundary of another room.

### Additional Objective

Furthermore, we may soon need to allow each user to divide his own room (aka "My Room") into two distinct spatial regions - one in which other users are free to build anything they want, and the other in which only the room's owner himself can build things. Such a division will enable partial control, thereby letting the user enjoy the benefits of both collaboration and privacy.

## Solution

### Restricted Zones

In order to implement the aforementioned mechanics, we need to come up with a new concept called "restricted zones". Each restricted zone is a rectangular region inside the voxel grid, within which the right to edit voxel blocks and persistent GameObjects is only granted to superusers. By "superuser", I mean:

- `Admin` user (if the room is of type `Hub`), or
- Either `Owner` or `Editor` of the room (if the room is of type `Regular`).

### Rules of Restriction

Here are non-superuser actions which must be prohibited inside restricted zones:

- Adding or removing a voxel block within the zone.
- Changing the texture of a voxel quad within the zone (except the out-facing quads on the zone's outermost edges).
- Adding a `GameObject` at a location which will make the object's collider (hitbox) intersect the zone's volume (except a `GameObject` whose `GameObjectConfig`'s `persistent` property is set to FALSE).
- Setting the transform of a `GameObject` to a position/direction which will make the object's collider (hitbox) intersect the zone's volume (except a `GameObject` whose `GameObjectConfig`'s `persistent` property is set to FALSE).
- Removing a `GameObject` whose collider (hitbox) intersects the zone's volume (except a `GameObject` whose `GameObjectConfig`'s `persistent` property is set to FALSE).

### Shape of a Zone

Each zone's volume is an axis-aligned box with voxel-based coordinates, whose range on the y-axis always extends all the way from the room's bottommost floor (y=0) to the topmost ceiling (y=8). This implies that each zone can be represented by the type shown below:

```typescript
export default class RestrictedZone extends EncodableData
{
  rowMin: number;
  rowMax: number;
  colMin: number;
  colMax: number;

  constructor(/*...*/) {/*...*/}
  //...

  getVolume(): AABB3
  {
    return {
      center: {
        x: 0.5 * (this.colMax + this.colMin + 1),
        y: 0.5 * (NUM_COLLISION_LAYERS * COLLISION_LAYER_HEIGHT),
        z: 0.5 * (this.rowMax + this.rowMin + 1),
      },
      halfSize: {
        x: 0.5 * (this.colMax - this.colMin + 1) - 0.01, // 0.01 = margin to ensure that voxel quads on the volume's outermost edges won't be under the restriction rule.
        y: 0.5 * (NUM_COLLISION_LAYERS * COLLISION_LAYER_HEIGHT) + 0.01, // 0.01 = extra padding to ensure that the volume covers the floor and ceiling quads
        z: 0.5 * (this.rowMax - this.rowMin + 1) - 0.01, // 0.01 = margin to ensure that voxel quads on the volume's outermost edges won't be under the restriction rule.
      },
    }
  }

  encode(bufferState: BufferState) {/*...*/}
  static decode(bufferState: BufferState): EncodableData {/*...*/}
  //...
}
//...
```

### Editing the Zones

- A room should be able to have up to 8 restricted zones, and only superusers must be able to add, remove, move, and scale these zones.

- In the UI, both `ConfigureMyRoomForm` and `ConfigureHubRoomForm` will need to have a new section called "Restricted Zones", with the tooltip icon which shows the following text on click: `Only you can edit things that are in the Restricted Zones.`. (Side Note: The "Editors" section of `ConfigureMyRoomForm` may eventually become deprecated, but that's another story; we won't worry about it for now).

- The aforementioned "Restricted Zones" section will have a 2D UI grid made up of `NUM_VOXEL_ROWS` number of rows and `NUM_VOXEL_COLS` number of columns (upon which editable UI boxes called `RestrictedZoneUIRect` can be placed), as well as a "+" IconButton (green) and a trash-can IconButton (red); the first button will be referred to as "addRestrictedZoneButton" and the second button will be referred to as "removeRestrictedZoneButton". "addRestrictedZoneButton" should be disabled whenever the total number of restricted zones has reached the maximum value (= 8), and "removeRestrictedZoneButton" should be disabled whenever no `RestrictedZoneUIRect` is currently selected.

- The width of the aforementioned 2D UI grid should nearly fill up the width of the popup form (except the margins) in case of a portrait-mode mobile screen, or stay at a reasonable size (narrow enough to ensure that the 2D UI grid's top and bottom are both fully visible within the popup form's panel at once) in case of a wide and/or landscape screen such as that of a PC, tablet, a mobile device in landscape mode, etc.

- Both the 2D UI grid and `RestrictedZoneUIRect` must be implemented as separate UI component types and be reused in `ConfigureMyRoomForm` and `ConfigureHubRoomForm`.

- Clicking the enabled "addRestrictedZoneButton" will create a new restricted zone inside the current room (`room.ts`), as well as its UI representation (i.e. `RestrictedZoneUIRect`) within the aforementioned 2D UI grid. `RestrictedZoneUIRect` is a color-filled rectangle with highlighted outlines and 8 draggable handles on the edges (4 at the corners (top-left, top-right, bottom-left, bottom-right) + 4 at the centers of the edges (top-center, bottom-center, left-center, right-center)). Dragging one of these handles will scale the zone by moving one or two of its edges, and dragging the inside of the rectangle itself will move the zone as a whole. Note that all movements must be discrete; the edges of the rectangle must always snap to the nearest voxel edges (i.e. grid lines). (Additional Hint: Think of `RestrictedZoneUIRect` as a rectangular selection inside an image-editing software, such as MS Paint).

- The 2D UI grid will probably need to be rendered as a square panel (with slightly concave borders to emphasize that it is a distinct input area - like that of `ChatTextInput`) which is filled with a moderately darker background (compared to that of the popup form) and have slightly lighter grid lines drawn on it. Note that there may also need to be some padding around the grid itself, in order to make it easy to view/edit the zones' edges which are aligned with the grid's boundary lines.

- Each time the user releases his pointer (e.g. mouse cursor) after making changes to a `RestrictedZoneUIRect` by dragging either its body or one of its handles, the corresponding zone's coordinates in the actual room data (i.e. `room.ts`) should be updated based on the way the `RestrictedZoneUIRect` changed its shape/position.

- A `RestrictedZoneUIRect` can either be in a selected state or an unselected state (When selected, its outline must be thicker and its colors should be accentuated in order to let the user know that it is selected). When the user creates a new `RestrictedZoneUIRect` by clicking "addRestrictedZoneButton", this new `RestrictedZoneUIRect` will be automatically selected. And whenever a `RestrictedZoneUIRect` gets selected, the previously selected `RestrictedZoneUIRect` will first be automatically unselected. When the user clicks either the currently selected `RestrictedZoneUIRect` or outside of its rectangular area, the currently selected `RestrictedZoneUIRect` will be unselected.

- "removeRestrictedZoneButton" will be enabled whenever a `RestrictedZoneUIRect` is selected. When the user clicks the enabled "removeRestrictedZoneButton", the currently selected `RestrictedZoneUIRect` will be removed, and its corresponding restricted zone will be removed from the actual room data (i.e. `room.ts`).

### Interaction with Restricted Zones

- Whenever a restricted zone gets added, removed, or modified, all the other clients in the same room (as well as the server) must immediately be notified of the change and sync up their own copies of the restricted zones (see the "Data Sync" section for more details). Subsequently, the zones' corresponding UI/gizmo representations should also refresh themselves in every client of the same room.

- When the client's current `GameMode` is "Edit Mode" (i.e. the user is editing the room), each of the room's restricted zones will be indicated by a red `WorldSpaceOutlineRect` whose world-space X/Z boundaries align with those of the zone's volume (The y-range of the volume will be ignored). The y-coordinate of this `WorldSpaceOutlineRect`'s position will always be equal to the y-coordinate of the camera's orbit-target.

- Whenever a non-superuser tries to do something that is prohibited due to the presence of a restricted zone, a notification message UI should briefly show up and say, "You are not allowed to edit this area!" (Hint: See `notificationMessageObservable` in `VoxelGameObject` and `CanvasGameObject`).

### Data Sync

Whenever a restricted zone gets created, destroyed, or modified (inside the client's `room.ts`), such a change must propagate through a chain of events to make sure that it is synced up across both the server and all the other clients in the same room (similar to how every change in `VoxelGrid` during the game gets synced up); that is, their local copies of the restricted zones (in `room.ts`) must always stay in sync. Make sure that, unlike the runtime memory (i.e. `roomRuntimeMemory.ts`), the room's binary data on the DB side (Firebase Cloud Storage) must not immediately save itself every time a change occurs in the restricted zones (It will be a waste of bandwidth). Instead, the room's binary data should simply continue saving itself periodically, just like before.

### Encoding of Restricted Zones

Each room's binary data (which is stored inside Firebase Cloud Storage) currently includes the room's `VoxelGrid` and `ObjectGroup` (see the `saveRoomContent` method in @src/server/db/util/dbRoomUtil.ts ). In order to save the room's restricted zones, we will need to encode them as part of `VoxelGrid`'s binary data. That is, besides encoding the individual voxels, we also need to encode the room's restricted zones within `VoxelGrid` before saving the whole thing (binary data) into a file. Don't forget that `VoxelGrid`'s own internal version migration logic for binary encoding should also be updated.

In order to integrate the restricted zones into `VoxelGrid`'s encoding scheme, we will need to add the array of restricted zones to `VoxelGrid` and augment its encode/decode methods to take account of this additional field.

```typescript
//...
export default class VoxelGrid extends EncodableData
{
  //...
  restrictedZones: RestrictedZone[];
  //...

  encode(bufferState: BufferState)
  {
    //...
    // TODO: encode the restricted zones
  }

  static decode(bufferState: BufferState): EncodableData
  {
    //...
    // TODO: decode the restricted zones
  }
  //...
}
//...
```

The binary encoding format of each `RestrictedZone` can be:

- 8 bits for rowMin (i.e. `EncodableRawByteNumber`)
- 8 bits for rowMax (i.e. `EncodableRawByteNumber`)
- 8 bits for colMin (i.e. `EncodableRawByteNumber`)
- 8 bits for colMax (i.e. `EncodableRawByteNumber`)

And the binary encoding format of the whole array of restricted zones can be:

- 8 bits for the number of zones in the room (i.e. `EncodableRawByteNumber`)
- 32 bits for zone #1 (i.e. `RestrictedZone`)
- 32 bits for zone #2 (i.e. `RestrictedZone`)
- 32 bits for zone #3 (i.e. `RestrictedZone`)
- ... etc
