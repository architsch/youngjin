# Admin System

Note: This plan is a follow-up from the previous door design refactoring work (see @docs/plans/2026/2026_08_27.md ).

## Problem

The current design enforces the following room-editing permission rules:

- Inside a Hub room:
    - Any user can edit any voxel/canvas within the room, except the main entrance door and anything close to it (see @docs/geometry/room_entrance.md ).
    - No user can change the room's core settings (e.g. `texturePackPath` and `editors`).
- Inside a Regular room:
    - Both the room's `Owner` and `Editor` can edit any voxel/canvas within the room, except the main entrance door and anything close to it (see @src/shared/room/util/roomValidationUtil.ts and @docs/networking/my_room.md ).
    - The room's `Visitor`, on the other hand, is not allowed to edit any voxel/canvas within the room.
    - Only the room's `Owner` can change the room's core settings (e.g. `texturePackPath` and `editors`).

This has been fine so far. The main issue with this approach, though, is that it provides no way for us to access the app as an admin and dynamically create Hub rooms & connect them to each other via custom doors, within the app itself rather than by means of a server-side script. This makes dynamic world-building exceptionally hard.

Hence, we should note that we are planning on having multiple doors in a room, which inevitably results in the establishment of a fairly sophisticated network (graph) of rooms and their mutual connections (where each room is a vertex and each pair of doors between two rooms is an edge). Formulating such a network purely on the basis of an autonomous algorithm (i.e. server-side script) renders human-driven design impossible.

## Solution

The most obvious solution to the aforementioned problem is to implement some kind of "admin privilege" which will be granted to one or more (very few) users for the purpose of reshaping not only the room's internal structure, but also the vast collection of rooms and their mutual relations.

We already do have `Admin` as a distinct `UserType`, yet no user has been given this type so far; and being an `Admin` has been bearing no practical difference whatsoever. We are going to change this.

### Admin Privilege

Changing a user's type to `Admin` is easy; since I am the one who owns the DB (Firestore), I can simply look up the app's DB collection and manually set the `userType` of the user to `Admin`. This part is straightforward and doesn't require any further elaboration.

The hard part is, "What should an admin be allowed to do?"

Here are some of the things which an admin must be allowed to do, if we are to grant him the full privilege to manipulate rooms and their interconnections:

1. An `Admin` must be able to change the `texturePackPath` of any Hub room.
2. An `Admin` must be able to add, remove, move, and change the metadata of any `DoorGameObject` inside any Hub room, via gizmos/UI which resemble those which become activated when a `CanvasGameObject` gets selected (Any user who is NOT an `Admin`, on the other hand, must not be allowed to add, remove, move, or change the metadata of any `DoorGameObject` inside a Hub room. In fact, for any user who is NOT an `Admin`, an `ObjectSelection` must not even be activated when a door is clicked; only instant transportation to the door's destination room should be conducted instead).
3. An `Admin` must be able to create a brand new Hub room (The current logic only lets the server automatically create an additional Hub only if all the existing Hub rooms are too crowded - see @docs/networking/room_population.md for details. We need to add a UI option for the `Admin` to create a Hub room manually).

### Door Semantics

A door's visual properties (e.g. colors) are already being encoded as part of its metadata (i.e. `InstancedMeshComposition` entry in the door's `ObjectMetadata`). In addition to this, we need to attach more types of metadata entries to door objects. In order to understand the underlying reasoning behind how these metadata entries are to be set up, however, we first need to understand some core concepts in regard to the new semantics of `DoorGameObject`.

#### Custom Door Labels

Each door (`DoorGameObject`) has a rectangular region called "label", which is more lightly colored than other parts of the door mesh. The label is empty by default, but an `Admin` user should be able to change the label's text to any arbitrary string. This text will be displayed upon the label (center-aligned both horizontally and vertically, with word-wrap but without any cut-off in the midst of a word) in the form of a world-space text which respects the rule of priority in rendering (i.e. Parts of it must be hidden when a mesh in front interferes with its view). The font's color can be something sensible and moderately (but not too emphatically) distinct from the background, such as a slightly dark shade of gray.

A door's label text, however, is not just for display purposes. It can also be used to uniquely identify a door, thereby allowing the client (who is traveling to another room) to choose the specific door at which the player is bound to spawn in the destination room (by including the label text as part of the `RequestRoomChangeSignal`).

#### Default Entrance vs Custom Entrance

- An `Admin` user should be able to mark each door as either a "default entrance" or "custom entrance" (by means of a metadata entry).

- As far as I recall, the current "entrance door" object in every multiplayer room (which is situated at `MULTI_PLAYER_ENTRANCE_VOXEL_COL` & `MULTI_PLAYER_ENTRANCE_VOXEL_ROW`) is a purely client-side object, never populated on the server-side (DB). If this is correct, we will need to add the appropriate server-side entrance door object to the room's DB representation (i.e. `DBRoom`) during version migration. If the entrance door has already been a part of the server-side data, on the other hand, the version migration logic will just need to attach the appropriate metadata to it. Note that the existing "entrance door" should be marked as "default entrance".

- When the server creates a new multiplayer room (Hub or Regular), this new room's `MultiplayerRoomBuilder` logic will now add a server-side "default entrance" door at where the main entrance door used to be (see @docs/geometry/room_generation.md to learn how room generation works). And this default door must reside in the server-side binary room data.

- Each new door, that is manually added by an `Admin` user, must be initially marked as "custom entrance".

- The main entrance door (as explained in @docs/geometry/room_entrance.md ) used to have a safety region around it (i.e. voxel with an invisible collision box + voxels where editing is prohibited, etc). Now that `DoorGameObject` is just an ordinary wall-attached object, however (just like `CanvasGameObject`), such a safety region should no longer exist (Note: `MultiplayerRoomBuilder` may still need to have some area of reservation for a newly generated room's default entrance door, though, during procedural room generation).

- When a player (client) requests to join a room, the server must determine the player's spawn hotspot based on the following logic:
```
let spawnHotspot: ObjectTransform | undefined = undefined;

if (/* RequestRoomChangeSignal contains the label text of the destination room's desired "destination door" (i.e. The door behind which the incoming player wishes to spawn) */)
{
    // The server will search for the door object of the given label inside the destination room.

    if (/* At least one door with the given label is found */)
    {
        spawnHotspot = /* Randomly pick one of the doors that have the given label, and grab its transform data */;
    }
}

if (!spawnHotspot)
{
    if (/* There is at least one default entrance door inside the destination room */)
    {
        // The server will randomly pick one of the default entrance doors and spawn the player right behind it.
        spawnHotspot = ...
    }
    else if (/* There is at least one custom entrance door inside the destination room */)
    {
        // The server will randomly pick one of the custom entrance doors and spawn the player right behind it.
        spawnHotspot = ...
    }
    else // There is NO door at all inside the destination room
    {
        // The server will simply spawn the player at the center of the room.
        spawnHotspot = ...
    }
}

// Proceed to spawn the player at "spawnHotspot":
// ...
```

#### Customizable Door Metadata

`DoorGameObject` will need to acquire the following new object metadata keys:

1. `DoorLabel`: When set, this value will be displayed as a world-space text right upon the door's "label" region. This is also the same string value which will be searched for by the server when choosing the incoming player's spawn hotspot under the presence of the destination door label parameter in `RequestRoomChangeSignal`.
2. `DestinationRoomId`: This is the ID of the destination room. When set, it lets the user visit the destination room by entering the door. If empty or undefined, a simple UI notification should show up and say: "This door is locked!".
3. `DestinationDoorLabel`: This is the `DoorLabel` metadata of the "destination door", which is assumed to be available inside the destination room. When the client requests to join the destination room, it will be attaching the door's `DestinationDoorLabel` metadata value to the `RequestRoomChangeSignal` as a parameter. The server will then look at this metadata value, search for the door (inside the destination room) whose `DoorLabel` metadata value matches the given parameter, and spawn the player right behind that door (If either such a door is not available or the parameter is empty, an available default entrance door will be chosen instead. If multiple doors happen to match the given parameter, a random one of them will be chosen).
4. `DoorType`: This will mark the door as either a "default entrance" or "custom entrance" (probably by means of a new type called `DoorType`, implemented in a manner similar to how `RoomType` is defined). When it is set to "default entrance", it will be used as a candidate for the incoming player's default (fallback) spawn location when `RequestRoomChangeSignal`'s destination door label parameter is empty (If the room does NOT contain any default entrance door, however, custom entrance doors will be used as the candidates for the spawn location instead - as a fallback).

### Door Physics

- Currently, each multiplayer room's main entrance door (located at `MULTI_PLAYER_ENTRANCE_VOXEL_COL`, `MULTI_PLAYER_ENTRANCE_VOXEL_ROW`) has the wall behind it removed (i.e. 5 voxel blocks), in order to let players spawn right behind the door's mesh and smoothly enter the room through the door without any physical (collision-related) interference (see @src/shared/physics/util/physicsCollisionUtil.ts ). I think we just need to fill this wall with solid blocks (during each room's version migration process) because:
    1. The presence of solid blocks behind the door will probably no longer interfere with the player's initial room-entering motion, since `PlayerController` enforces the player's movement in some fixed way while the player is still overlapping the door's voxel (But I am not totally sure about this, so check to see if there might be an undesirable side effect).
    2. `DoorGameObject` is now a wall-attached object, so clearing out the voxel blocks behind it directly contradicts the logic of wall-attachment (see @docs/geometry/wall_attached_object.md ).

- Since the "entrance voxel" is no longer a fixed spot that is globally known (due to the fact that doors can now be manually placed at arbitrary locations), We will have to refactor the way in which `PlayerController` enforces the player's initial sliding movement when entering the room through a door. Instead of assuming that the player spawned at the voxel located at `MULTI_PLAYER_ENTRANCE_VOXEL_COL` & `MULTI_PLAYER_ENTRANCE_VOXEL_ROW`, `PlayerController` ought to first record the player's initial position/direction as soon as it spawns, and enforce a brief sliding motion based on that position/direction.

### New UI Components

What's shown below are some of the new UI flows which must be implemented.

#### World-Space Interactions

- When a non-`Admin` user selects a wall's voxel quad, the same exact UI options should show up as before - an option to remove the voxel block, an option to add a voxel block, and an option to add a canvas. When an `Admin` user selects a wall's voxel quad, however, an additional option for adding a door (i.e. `DoorGameObject`) to that wall should show up, and let the user proceed to do that if the area of the wall is wide enough to support a door (similar to how adding a `CanvasGameObject` works).

- When a non-`Admin` user clicks a door while its PlayerProximityDetection is active, he will immediately be transported to the door's destination room (if the destination room exists). When an `Admin` user clicks a door, on the other hand (regardless of whether PlayerProximityDetection is active or not), the door's `ObjectSelection` will be activated and door-related UI option components will show up in `ObjectSelectionMenu`. Also, clickable world-space arrows will show up (just like in the case of `CanvasGameObject` selection) which will let the user move the door's position.

#### Door Manipulation UI

When a door is selected by an `Admin` user, its corresponding `ObjectSelection` becomes activated. During the activation, the bottom UI (`ObjectSelectionMenu`) should behave in the following manner:

1. If the user is in Play Mode, it should simply show a button named "Enter". Clicking this button will have the same effect as when a non-`Admin` user clicks the door (i.e. It will instantly teleport the user to the door's destination room).
2. If the user is in Edit Mode, `ObjectSelectionMenu` should display the following option buttons (via a new UI class called `DoorEditOptions`):
    - A "remove door" IconButton, which works similarly to the `TrashIcon` button in `CanvasEditOptions`.
    - A "change label" IconButton (with an icon that symbolically represents text input). When clicked, it brings up a popup form which lets the user enter any arbitrary text via the existing `FormTextInput` component, and hit the "Apply" button right next to it to set the door's `DoorLabel` metadata value to the text entered. As soon as this metadata value changes, the door's label should start displaying this new text.
    - A "change destination" IconButton (with an icon that symbolically represents the concept of "destination" - maybe a map marker symbol on a road?). This, too, will bring up a popup form when clicked. This popup form, however, will show a list of rooms from which the user can choose which one to set as the destination.
        - For this UI, just use the existing `RoomListForm`; but make sure that every "Visit" button will be a "Choose" button instead (which, when clicked, will let the user "choose" the corresponding room's ID as the destination room ID and assign it to the door's `DestinationRoomId` metadata value, in a way similar to how the `ImageChooser` UI works). If the list entry's room is already set as the door's destination room, the "Current Destination" text should be displayed in place of the "Choose" button (and such an entry must be shown on top of the list).
        - Also, `RoomListForm` should no longer have either the "Login to create your own room" entry or the "My Room" entry; in place of such entries, instead, we need to have a special entry titled "Create a new Hub" with a "Create" button next to it, besides the aforementioned "Current Destination" entry. When the "Create" button is clicked, the client will be sending a `createRoom` request to the server via `RoomAPIClient` (see @src/client/networking/client/roomAPIClient.ts ) so as to be able to create a new Hub room (We may need an additional parameter in the request to specify the type of the room that the client wants to create, and let the server approve of such a Hub-creation request only if the requester is an `Admin`). When the server approves this request and finishes creating a new Hub room, the client's loading screen will go away, a "success" notification UI will show up, and the room list UI will reload itself to show the new Hub room's list entry alongside the others.
        - Beneath the list of room entries, we will also need an additional text input through which the user can set the door's `DestinationDoorLabel` metadata value (Use the existing `FormTextInput` component for this).
    - A "customize apperance" IconButton (with an icon that symbolically represents a paint brush). When clicked, it temporarily places a (horizontally scrollable) bottom UI bar which contains options to tweak the shader/material parameters of the selected door's mesh instance such as the colors of the panels/mouldings, etc (i.e. any parameters that are currently being encoded in the door's `InstancedMeshComposition`-type object metadata). This new bottom UI bar will be based on a new type of UI component called `CustomizeDoorForm`, and will be carrying a "Close"(X) button above its upper-right corner which lets the user dismiss `CustomizeDoorForm` when clicked (Hint: When implementing `CustomizeDoorForm`, use the existing `CustomizePlayerForm` as a reference). Note that any changes in the shader/material parameters must be instantly be reflected in the door's appearance, so that the user will be able to monitor the changes in real time.
    - A "configure door settings" IconButton (with the existing `GearIcon`). When clicked, it brings up a popup form with a checkbox in it (Use the existing `Checkbox` component for this). This checkbox's label text will be "Use this door as a default entrance". Whenever this checkbox is enabled, the door's `DoorType` metadata will become "default entrance". When disabled, the door's `DoorType` metadata will become "custom entrance".

#### Hub Room Configuration Form for the Admin

Let us have a new UI popup form called `ConfigureHubRoomForm`. It is almost identical to `ConfigureMyRoomForm`, except that it only includes the section that allows the admin to change the room's `texturePackPath`.

Inside any Hub room, an `Admin` user should be able to open up `ConfigureHubRoomForm` by clicking the "Room Settings" button underneath the "startEditingButton" component in `GameModeMenu`.

#### Temporary Route for the Login UI Flow

Since the "Login" button is no longer exposed to the client, due to the fact that this button will be hidden from `RoomListForm` and the form itself will no longer be shown to non-`Admin` users, we need to add a new debug-command (i.e. "login") in the `TextInput` component of `DebugStats`. When executed, this debug-command will bring up the `AuthPromptForm` popup just as though the "Login" button inside `RoomListForm` is clicked.

### Additional Implementation Tips

- The server will probably need to have its own module for the logic which determines the incoming player's spawn hotspot (e.g. destination door), just like how `RoomPickerUtil` handles the logic which determines the user's initial room.

- `RoomValidationUtil` should be the central place where admin-related logic is being handled.
