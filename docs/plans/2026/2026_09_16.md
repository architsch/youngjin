# New InstancedMeshComposition System

Last Updated: 2026-09-17

## Problem

The existing `InstancedMeshComposition` system ( @docs/graphics/instanced_mesh_composition.md ) is versatile enough to assemble mesh instances in any way we can imagine. When it comes to optimization and other technical considerations, however, it reveals the following major weak points:

1. The default encoder (`DefaultCompositionCodec`) encodes data way too inefficiently. For example, it uses multiple characters to encode a piece of information which requires only a fraction of a character.
2. The default encoder (`DefaultCompositionCodec`) is not versatile enough to be used as a "universal encoder" for a number of fairly simple types of mesh composition, such as those of `CanvasGameObject`, `DoorGameObject`, and `WallLampGameObject`. It is either due to the mismatch of parameters or the relatively higher encoding-inefficiency compared to custom codecs (e.g. `CanvasCompositionCodec`, `DoorCompositionCodec`, etc).
3. The default encoder (`DefaultCompositionCodec`) does not encode spatial coordinates accurately due to errors in its quantization scheme. This yields undesirable results such as mesh instances slightly overlapping each other.
4. Some geometries, which can be expressed as collections of simpler geometries (e.g. The "Box" geometry which is just a collection of 6 squares), are being drawn using separate InstancedMeshes. This tends to unnecessarily increase the total number of draw calls, which leads to poorer performance.

For the sake of optimization, architectural simplicity, and accuracy, we need to come up with a more elegant way of encoding mesh compositions - a new approach that is powerful enough to mitigate the problems listed above.

## Solution 1

### The 'Shape' Type

Here is a way to reduce the total number of draw calls (InstancedMeshes) without refactoring the existing `InstancedMeshComposition` system too much. We can simply let each `InstancedMeshCompositionPart` represent a `Shape`, which can be expressed as an assembly of one or more mesh instances (not just one). A "Box" shape, for example, could be expressed as 6 instances of the "Square" InstancedMesh, each of which makes up each side of the box. The following code demonstrates the way it should be defined (I am defining `Shape` as a numerical type in order to make the encoding process straightforward):

```typescript
// Should be located at `src/shared/graphics/mesh/types/shape.ts`:

export type Shape = number;

export const ShapeEnumMap: Record<string, number> =
{
    Square: 0,
    Box: 1,
    Cylinder: 2,
}
```

### Two Layers of Composition (Part and its Components)

With this new `Shape` type, each `InstancedMeshCompositionPart` can now represent not just a single mesh instance, but also multiple mesh instances. What is shown below is the new definition of `InstancedMeshCompositionPart`:

```typescript
export default interface InstancedMeshCompositionPart
{
    shape: Shape,
    materialId: string,
    dir: Vec3,
    offset: Vec3,
    scale: Vec3,
    [key: string]: any, // arbitrary optional properties
}
```

Each of the mesh instances which belong to an `InstancedMeshCompositionPart`, then, can be represented by a new type called `InstancedMeshCompositionPartComponent`. Think of `InstancedMeshCompositionPart` as a group of one or more `InstancedMeshCompositionPartComponent`s.

```typescript
export default interface InstancedMeshCompositionPartComponent
{
    instancedMeshId: string,
    dir: Vec3,
    offset: Vec3,
    scale: Vec3,
    [key: string]: any, // arbitrary optional properties
}
```

The `refreshInstancedMeshes` method in `InstancedMeshComposer`, then, should be able to visit each individual `InstancedMeshCompositionPart`, access its components (i.e. `InstancedMeshCompositionPartComponent`s), and refresh them.

```typescript
const parts = this.instancedMeshComposition.parts;
for (let i = 0; i < parts.length; ++i)
{
    const part = parts[i];

    const partComponents = CompositionPartComponentsConstructorMap[part.shape](part);
    for (let j = 0; j < partComponents.length; ++j)
    {
        const partComponent = partComponents[j];

        const instancedMeshId = partComponent.instancedMeshId;
        let nextIndex = this.nextIndexByInstancedMeshIdTemp[instancedMeshId];
        //...
    }
}
```

### Shortcut for InstancedMeshId

Quick and efficient access of instancedMeshIds can be achieved through the following new map type:

```typescript
// Should be located at 'src/shared/graphics/mesh/maps/instancedMeshIdMap.ts`:

const m: string[] = new Array<string>(64);

function register(geometryId: string, materialId: string)
{
    m[GEOMETRY_CODE_BY_ID[geometryId] * 8 + MATERIAL_CODE_BY_ID[materialId]] = MeshDataUtil.getInstancedMeshId(geometryId, materialId);
}
register("Square", INSTANCED_EMISSIVE_MATERIAL_ID);
register("Square", INSTANCED_TIN_MATERIAL_ID);
register("Cylinder", INSTANCED_TIN_MATERIAL_ID);
register("Square", INSTANCED_WOOD_MATERIAL_ID);
register("Cylinder", INSTANCED_WOOD_MATERIAL_ID);

const InstancedMeshIdMap =
{
    getInstancedMeshIdByCodes: (geometryId: number, materialId: number): string =>
    {
        return m[GEOMETRY_CODE_BY_ID[geometryId] * 8 + MATERIAL_CODE_BY_ID[materialId]];
    },
}

export default InstancedMeshIdMap;
```

## Solution 2

### Compact/Universal DefaultCompositionCodec

Another main cause of inefficiency is that the default encoder (`DefaultCompositionCodec`) separately encodes the geometry ID, material ID, offset, direction, scale, and material-specific properties of every single mesh instance inside the composition.

And here is yet another flaw in the default encoder. It currently encodes offsets and scales using some arbitrary quantization standards, which causes slight spatial misalignments in world space (such as canvases & wall-lamps not perfectly aligning their edges with their footprints, etc). This means that offsets and scales must be encoded with specific quantization steps in mind.

So, let me introduce a much better way of encoding a default composition which will solve the aforementioned issues. What is shown below is the improved encoding logic of `DefaultCompositionCodec`'s `encode` method:

```typescript
const materialCode = MATERIAL_CODE_BY_ID[part.materialId];
if (!materialCode)
{
  console.error(`DefaultCompositionCodec::encode :: Material ID has no corresponding code (Material ID = ${part.materialId})`);
  continue;
}

// This base-94 character value encodes one of the 94 possible permutations between 'shape' and 'materialCode'. Here, I am assuming that the maximum possible value of 'materialCode' can potentially go up to 7.
partChars.push(StringUtil.convertRawNumberToVisibleASCII(shape * 8 + materialCode));

const dirVecCode = DirUtil.dirVecToCode(part.dir);
partChars.push(StringUtil.convertRawNumberToVisibleASCII(dirVecCode));

// Each quantization step of 'offset' must be 0.0625.
partChars.push(StringUtil.convertNumberToVisibleASCII(part.offset.x, -2.9375, 2.875));
partChars.push(StringUtil.convertNumberToVisibleASCII(part.offset.y, -2.9375, 2.875));
partChars.push(StringUtil.convertNumberToVisibleASCII(part.offset.z, -2.9375, 2.875));

// Each quantization step of 'scale' must be 0.125.
partChars.push(StringUtil.convertNumberToVisibleASCII(part.scale.x, -5.875, 5.75));
partChars.push(StringUtil.convertNumberToVisibleASCII(part.scale.y, -5.875, 5.75));
partChars.push(StringUtil.convertNumberToVisibleASCII(part.scale.z, -5.875, 5.75));

if (part.materialId == INSTANCED_WOOD_MATERIAL_ID)
{
    arr.push(StringUtil.convertRawNumberToVisibleASCII(ColorUtil.rgbToPaletteIndex("Timber", part.colorIndex))); // Color of the non-moulding portion of the wood
    arr.push(StringUtil.convertRawNumberToVisibleASCII(ColorUtil.rgbToPaletteIndex("Timber", part.mouldingColorIndex))); // Color of the moulding

    const thicknessStep = toThicknessStep(part.mouldingThickness); // See `CanvasCompositionCodec` for reference.
    const mouldingShape = part.mouldingIsConvex ? 1 : 0;
    const hideThisPart = part.hideThisPart ? 1 : 0; // When this flag is enabled, we must hide this InstancedMeshCompositionPart from view (Example use case: When a canvas's frame-type is set to "No Frame", the frame's InstancedMeshCompositionPart must have its 'hideThisPart' flag set to TRUE).
    const mouldingType = (mouldingShape << 1) | hideThisPart; // 'mouldingType' is a 2-bit number, so its range is [0, 3].

    // This base-94 character value encodes one of the 94 possible permutations between 'mouldingType' and 'thicknessStep'. Here, I am assuming that the total number of thickness steps will never exceed 11 and the total number of mouldingTypes will never exceed 8 (i.e. max number of 3-bit permutations).
    arr.push(StringUtil.convertRawNumberToVisibleASCII(mouldingType * 11 + thicknessStep));
}
else if (part.materialId == INSTANCED_EMISSIVE_MATERIAL_ID)
{
    arr.push(StringUtil.convertRawNumberToVisibleASCII(ColorUtil.rgbToPaletteIndex("Light", part.colorIndex)));
}
// Note: We probably don't even need to pad an empty character (" ") after every InstancedMeshCompositionPart because the 'decode' method can simply infer exactly where each InstancedMeshCompositionPart ends/begins based on which characters it is currently parsing and how many remaining characters are there to be decoded.
```

### Definition of dirVecCode

`dirVecCode` will be an index in `DIR_VEC_BY_CODE` (which is defined in `sharedConstants.ts`). For decoding (i.e. conversion of a direction vector to its corresponding code), we will need to add a new method called `dirVecToCode: (v: Vec3): number` to `dirUtil.ts`. There will be 6 `dirVecCode` values for now (0 = "-y", 1 = "+y", 2 = "-x", 3 = "+x", 4 = "-z", 5 = "+z"), although in the future we might consider adding more directions (such as diagonal ones).

### Prevention of Z-Fighting

When `DefaultCompositionCodec` decodes an `InstancedMeshCompositionPart` whose shape is of the "Square" type (i.e. flat surface), it should add a tiny offset to the local z-coordinate of its decoded position in order to prevent potential z-fighting. The reason why this is necessary is that a square shape, which is not a component of a 3D shape such as a box, is most likely to be a flat surface that is placed right upon another flat surface.

The question is, "How much z-offset should we give to each square shape, in order to prevent z-fighting?" This can be quite tricky to answer because there could be multiple layers of flat surfaces, in which case z-offsets will need to come in multiple levels. If there are 3 layers, for instance, the first layer's z-offset may need to be 0.005, second layer's z-offset may need to be 0.01, and the third layer's z-offset may need to be 0.015.

Encoding these slightly varying z-offsets as part of the `InstancedMeshComposition` object metadata (i.e. base-94 characters) is both wasteful of resources and error-prone. Instead, we need a procedural way of computing these z-offsets, which is demonstrated below:

```typescript
const squareParts: InstancedMeshCompositionPart[] = [];
const squarePartZIndices: number[] = [];
for (const part of decodedParts)
{
    if (part.shape == ShapeEnumMap.Square) // InstancedMeshCompositionPart is a single square (flat surface)
    {
        squareParts.push(part);
        squarePartZIndices.push(1);
    }
}
for (let i = 0; i < squareParts.length; ++i)
{
    for (let j = i-1; j >= 0; --j)
    {
        const curr = squareParts[i];
        const prev = squareParts[j];
        if (Vector3DUtil.equal(curr.dir, prev.dir)) // squares are parallel
        {
            // Note: 'Geometry3DUtil.squaresIntersect' is not implemented yet.
            if (Geometry3DUtil.squaresIntersect(curr.pos, curr.dir, prev.pos, prev.dir))
            {
                // If two squares in the list are parallel and they intersect each other, the one which comes after the other must be sitting on top of the one which comes before.
                squarePartZIndices[i] = squarePartZIndices[j] + 1;
                break;
            }
        }
    }
}
for (let i = 0; i < squareParts.length; ++i)
{
    const squarePart = squareParts[i];
    const zOffset = 0.005 * squarePartZIndices[i];
    const zOffsetVec = Vector3DUtil.scale(Vector3DUtil.normalize(squarePart.dir), zOffset);
    squarePart.pos = Vector3DUtil.add(squarePart.pos, zOffsetVec);
}
```

### Canvas, Door, and WallLamp

Once we are done upgrading the encoding scheme of `DefaultCompositionCodec`, we will probably need to do the following things:

1. It may be a good idea to make both `CanvasGameObject` and `DoorGameObject` encode their mesh compositions using `DefaultCompositionCodec` instead of their own custom codecs (i.e. `CanvasCompositionCodec` and `DoorCompositionCodec`). This transition may require us to use more characters for encoding (while also requiring us to add a version migration for automatic format conversion), but the resulting simplicity (unity) in code will make future problem-solving significantly easier. I am not totally sure about the benefit of doing this, though, so please tell me if you disagree with my reasoning here.

2. We will also need to re-encode `WallLampGameObject`'s pre-encoded composition data (see @src/server/ssg/builder/preEncodedCompositionBuilder.ts), so as to ensure that the format is up to date. Before doing this, of course, we will first have to update the logic of `PreEncodedCompositionBuilder` to make sure that it is compatible with the new encoding scheme of `DefaultCompositionCodec`.
