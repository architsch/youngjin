# Object Installation Preview Logic

## References

- `VoxelQuadPlacementOptions`: @src/client/ui/components/hud/selection/voxelQuadPlacementOptions.tsx
  - "addCanvasButton" is used for adding a new `CanvasGameObject`.
  - "addPropButton" is used for adding a new `PropGameObject`.
- `CanvasEditOptions`: @src/client/ui/components/hud/selection/canvasEditOptions.tsx
  - "changeCanvasImageButton" is used for changing the canvas's imagePath.
  - "changeCanvasFrameButton" is used for changing the canvas's compositionIndex.
- `PropEditOptions`: @src/client/ui/components/hud/selection/propEditOptions.tsx
  - "changePropImageButton" is used for changing the prop's imagePath.
- `ImageMapThumbnailPanel`: @src/client/ui/components/panel/imageMapThumbnailPanel.tsx
  - Selecting one of the listed thumbnails sets the object's imagePath.
- `CompositionThumbnailPanel`: @src/client/ui/components/panel/compositionThumbnailPanel.tsx
  - Selecting one of the listed thumbnails sets the object's compositionIndex.

## Problem

Here is the current UI flow:

1. When the user clicks "addCanvasButton" or "addPropButton" in `VoxelQuadPlacementOptions`, it immediately adds the corresponding `GameObject` to the world without asking the user to choose the object's imagePath and/or compositionIndex.
2. This new `GameObject`'s imagePath and/or compositionIndex are initialized either randomly or based on a procedure that is outside of the user's control.
3. The user then needs to manually select "changeCanvasImageButton"/"changeCanvasFrameButton" in `CanvasEditOptions` (or "changePropImageButton" in `PropEditOptions`) to open up `ImageMapThumbnailPanel`/`CompositionThumbnailPanel` and select the desired option there, in order to customize the object.

The problem with this approach is that the user is forced to first see the new object being stylized in a way which may not match what he expected, and then manually find/click a button once again to adjust it. This is way too cumbersome, and many people might even miss this extra step entirely and simply assume that the object they are seeing is in its final and immutable form.

## Solution

The solution is to first prompt the user to select the new object's imagePath and/or compositionIndex before/while adding it. What's shown below are the new UI flows I am proposing:

### New UI Flow for CanvasGameObject Placement

1. When the user clicks "addCanvasButton" in `VoxelQuadPlacementOptions`, we should first highlight "addCanvasButton" (in a manner similar to "changeCanvasImageButton" in `CanvasEditOptions`) and show `ImageMapThumbnailPanel` above `VoxelQuadPlacementOptions`. This `ImageMapThumbnailPanel` will have none of its thumbnails selected yet, although its initial scroll position and category tab will be what they were the last time a `CanvasGameObject`'s `ImageMapThumbnailPanel` was closed. If it is the very first time that a `CanvasGameObject`'s `ImageMapThumbnailPanel` has ever opened since the beginning of the client app's runtime, the scroll position and category tab should be at their leftmost elements by default (i.e. "First item" for the scroll-list, "All" for the category tab).
2. If the user selects one of the thumbnails, a new `CanvasGameObject` with the selected imagePath and the "no frame" compositionIndex will be added and it will be auto-selected (i.e. its `ObjectSelection` will be activated). If the user just closes `ImageMapThumbnailPanel` without selecting any thumbnail, on the other hand, "addCanvasButton" will be un-highlighted and `VoxelQuadPlacementOptions` will resume its original UI state.
3. As soon as the `CanvasGameObject` is added, `ImageMapThumbnailPanel` will be immediately closed, `VoxelQuadPlacementOptions` will be replaced by `CanvasEditOptions`, its "changeCanvasFrameButton" will be highlighted, and `CompositionThumbnailPanel` will show up above `CanvasEditOptions`. This `CompositionThumbnailPanel` will have none of its thumbnails selected yet (the rest of its UI initialization logic will follow that of `ImageMapThumbnailPanel`).
4. If the user selects one of the thumbnails, the selected `CanvasGameObject`'s frame will be set to the one corresponding to the selected thumbnail, and `CompositionThumbnailPanel` will be immediately closed, thereby leaving only `CanvasEditOptions` with none of its buttons highlighted (This immediate closure of `CompositionThumbnailPanel` upon thumbnail selection, however, should happen only during object installation and not during its subsequent edits). If the user just closes `CompositionThumbnailPanel` without selecting any thumbnail, on the other hand, the `CanvasGameObject`'s frame will simply stay as "no frame".

### New UI Flow for PropGameObject Placement

1. When the user clicks "addPropButton" in `VoxelQuadPlacementOptions`, we should first highlight "addPropButton" (in a manner similar to "changePropImageButton" in `PropEditOptions`) and show `ImageMapThumbnailPanel` above `VoxelQuadPlacementOptions`. This `ImageMapThumbnailPanel` will have none of its thumbnails selected yet, although its initial scroll position and category tab will be what they were the last time a `PropGameObject`'s `ImageMapThumbnailPanel` was closed. If it is the very first time that a `PropGameObject`'s `ImageMapThumbnailPanel` has ever opened since the beginning of the client app's runtime, the scroll position and category tab should be at their leftmost elements by default (i.e. "First item" for the scroll-list, "All" for the category tab).
2. If the user selects one of the thumbnails, a new `PropGameObject` with the selected imagePath will be added and it will be auto-selected (i.e. its `ObjectSelection` will be activated). If the user just closes `ImageMapThumbnailPanel` without selecting any thumbnail, on the other hand, "addPropButton" will be un-highlighted and `VoxelQuadPlacementOptions` will resume its original UI state.
3. As soon as the `PropGameObject` is added, `ImageMapThumbnailPanel` will be immediately closed and `VoxelQuadPlacementOptions` will be replaced by `PropEditOptions` (This immediate closure of `ImageMapThumbnailPanel` upon thumbnail selection, however, should happen only during object installation and not during its subsequent edits).

### Others

Besides the two new UI flows which I illustrated above, we need to apply analogous UI flow revisions to the rest of the manually installable objects (i.e. `LampGameObject`, `DoorGameObject`, and `LabelGameObject`). The reason behind this is that, when it comes to the matter of consistency (both from the standpoint of software architecture and user experience), it makes sense to unify the UI flows of ALL object installation processes as much as possible.
