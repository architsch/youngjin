# LabelGameObject

Let's implement a new type of object called `LabelGameObject`, whose design will be mostly identical to that of `CanvasGameObject` (i.e. in the sense that it has an adjustable frame and a dynamically rendered inner area, and is only attachable to the wall), except that it is designed to render a text via `LabelText` ( @src/client/object/components/labelText.ts ) just like what `DoorGameObject`'s label part does. In order to make `LabelGameObject` exhibit its text in a good-looking and efficient manner, however, we need to resolve the issues listed below:

## Scale-Sensitive LabelText Component

The existing `LabelText` ( @src/client/object/components/labelText.ts ) GameObjectComponent enforces the label's world-space area to be of a fixed offset and size. This works well with `DoorGameObject` ( @src/shared/object/types/objectTypeConfig/doorObjectTypeConfig.ts ) which is fixed in size, but it won't work well with any type of object whose size can be modified (including the `LabelGameObject` type we are trying to implement). Therefore, we will probably need to reformat the `labelText` component-config of `ObjectTypeConfig` ( @src/shared/object/types/objectTypeConfig/objectTypeConfig.ts ).

First of all, the `localOffset` and `size` properties of the `labelText` component-config are not so cleanly laid out and prone to misinterpretation. Instead of having these two properties which were originally designed to assign a fixed offset and size to the label, we should probably just have a single property called `localTransform`, like the one shown below:

```typescript
labelText?: {
    localTransform: Transform, // Local offset, local direction, and local scale of the label-area, relative to the object's transform.
    //...
},
```

The new type called `Transform` can be one of the following two alternatives. First of all, if there is supposed to be anything special about `ObjectTransform` as opposed to a more generic type called `Transform`, we will need to introduce a new type called `Transform` and make the existing `ObjectTransform` type inherit from it, like what's shown below:

```typescript
export default class Transform extends EncodableData
{
    //...
}
```
```typescript
export default class ObjectTransform extends Transform
{
    //...
}
```

If there is nothing special about a transform which is bound to a GameObject compared to a transform which exists on its own, then I guess we can simply rename `ObjectTransform` to `Transform`.

## Variable-Size Allocation of the Label-Atlas Texture

Since `LabelGameObject` is supposed to be resiable, we cannot simply allocate a label-atlas texture cell of a fixed size. The fixed-size allocation scheme worked fine because every `DoorGameObject`'s label has the same exact size. Now that we are going to have label areas which can be of any size within its range (Note: Let us assume that `LabelGameObject`'s min/max sizes are the same as those of `CanvasGameObject`), we need a much larger and square-shaped label-atlas texture and a dynamic texture cell allocation algorithm which is more or less a 2D equivalent of the C programming language's dynamic heap allocation logic (i.e. `malloc(...)`). My idea is that, in the beginning, we may partition the label-atlas texture into cells of size 0.5x0.5 (because that's the smallest unit (step) in which the label object can be resized). Then, whenever a `LabelGameObject` wants to render a text in its label area and it doesn't have its own portion of the atlas texture reserved yet, we will need to first compute the dimension of the texture area which will need to be allocated (in terms of those cells, each of which is of size 0.5). So, for a `LabelGameObject` whose label's area is 2.5x3 in world space, for example, we will need to allocate a region in the label-atlas texture which fits a grid of cells, consisting of 5 columns (because 2.5 / 0.5 = 5) and 6 rows (because 3.0 / 0.5 = 6). The trick is to figure out exactly where in the label-atlas this particular grid of cells should fit. I think we ought to ensure the maximmum compactness of the allocated areas by doing some kind of "Tetris" with these grids of cells, trying not to produce any irregular edges as much as possible (because they are likely to generate small gaps in which labels of most sizes won't be able to fit); otherwise, spaces will be wasted and we might even need to run a separate compaction process at some point.

The aforementioned texture-allocation logic is pretty complex in itself, so I think we should create a separate utility class called `TextureAllocationUtil` or something (If you have a better idea for its name, tell me), instead of putting the allocation logic within the existing `TextureUtil` ( @src/client/graphics/util/textureUtil.ts ).

## User-Defined Font Size

Right now, `LabelText` dynamically shrinks/expands the text's size based on the number of characters and the area in which they are supposed to fit. While this adaptive approach makes it easy for the user to just enter the text and see it fit inside the label nicely, it sort of limits the degree of freedom. So, let's add a checkbox to the font customization UI panel called "Auto Size" (just like in Unity game engine's TextMeshPro UI component). When it is enabled, `LabelText` will automatically shrink the font size to make sure that the text fits inside the area (which is the current behavior). If it is disabled, the font size will be whichever value that is specified by the user (This "Font Size" value will be tweakable via a slider with a decent number of steps. The slider itself must be disabled when the "Auto Size" checkbox is enabled). This font size should be based on pixels, and the size of each pixel in world-space must be constant regardless of the size of the area reserved by `LabelText`. (Note: By default, "Auto Size" must be enabled)

The text's character limit should be a lot bigger (i.e. Up to 512 characters should be tolerated). If the characters happen to overflow due to the fact that the label's area is too small to contain them all, those characters should just get cut off underneath the bottom of the area.

Text-wrapping should still be automatic; The text input UI element consists of just 1 line of text area for entering characters, so letting the user manually enter a "next line" character there will be too tricky.

All of the aforementioned text/font-related parameters must be controllable via UI in any object with the `LabelText` component in it (That is, both `LabelGameObject` and `DoorGameObject`).

## Note on Architecture

As you have noticed, we now have multiple object types (e.g. `CanvasGameObject`, `LampGameObject`, `LabelGameObject`) which have adjustable moulding-based frames. Both the underlying logic (e.g. `InstancedMeshCompositionCodec`) and the UI (e.g. panel for editing the frame's properties) for this can be unified under a generic set of modules, instead of being replicated for every one of these object types. So, please investigate to see how far you can abstract away the redundant pieces of logic.

## Special Rule

For now, let's only allow `Admin`-type users to add/modify/remove a `LabelGameObject` (just like `DoorGameObject`).
