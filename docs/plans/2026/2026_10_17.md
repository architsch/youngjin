# Creatures

## Goal

Creatures are pets that a user raises as companions. They follow the user from room to room, wander freely, and act on their own needs: a hungry one goes to a vending machine or a plate and takes some food, a bored one watches a TV or listens to a radio. They also interact with each other.

As in The Sims, the user controls them only indirectly, through the existing edit mode: by how certain types of objects are distributed in the room, and by their subtypes (e.g. the `ImagePath` of a `PropGameObject` or a `CanvasGameObject`).

## Decisions (2026-10-17)

- **`src/core` is human-reserved.** It holds code hand-written by the user alone, with no chance of direct modification by an AI agent.
  - Claude writes only its initial, very minimal boilerplate, for the user to read, understand and fill in.
  - After that, `client`, `server` and `shared` import from it.
- **`src/core` is Apache-2.0**, like the rest of `src/`.
- **`src/core` imports nothing from outside `src/core`**, enforced by a test, so that the separation between human-written code and AI-written code stays clean.
- **Presence.** Creatures exist only while their owner's player character is present in the room. Leaving or disconnecting removes them.
- **Party.** Every creature a user owns is out with them, so a per-user ownership limit is needed.
  - A room's creature cap sizes every client's mesh pools.
  - A joining user whose creatures don't fit under the cap keeps the rest away until their next room change.
  - The values are to be proposed from measurements.
- **First creature.** How a user gets one is decided later. Until then, only admins and dev sandboxes can spawn creatures.
- **Look (v1).** The player's body parts (`PlayerCompositionCodec`), drawn small, as NPCs reuse them. An animal-shaped look comes later.
- **Fans push creatures.** The user's design: the server tells the client the creature's destination, and the client reports back when the creature can't reach it.
- **Offer map.** Which picture offers what to a creature is a curated map in `src/shared`, keyed by picture path (paths are permanent), and written in core's vocabulary of offer kinds.
- **Hard guards deferred.** The OS sandbox's write deny and similar measures are left for later.

## Who runs what

**The server decides; the owner's client moves.**

- **The server owns the creature's state and choices.** Needs, the next intent, leased claims on offers (one plate, two creatures), creature-to-creature interactions and progression all live there. Validating client-reported actions would need the same state and logic, and progression must never be self-reported.
- **The owner's client carries the intent out.** It uses the player's movement stack, so fans push creatures as they push players:
  - `Rigidbody` handles gravity, step-up and fan forces;
  - `PeriodicTransformEmitter` runs on the owner, and `PeriodicTransformReceiver` on everyone else.
- **A new `CreatureController`** steers along a path, re-paths when it is pushed off course, and reports arrived or failed against the intent's sequence number.
  - The server checks a claimed arrival against the position it holds, with a timeout as the backstop.
  - Failure feeds `CreatureBrain.finish(..., false)`.
- **Only the owner may move a creature.** If every client moved it, each would be blown differently and their reports would disagree. Server-stepped physics would cost a server tick and feel different from fans tuned at 60 fps.
- **Accepted costs:**
  - creature transforms stream like players' while a creature moves;
  - a creature pauses while its owner's tab is hidden, as the owner's player does;
  - movement is trusted as players' movement already is.
- **Single-player rooms** run the decision host on the client too.

Estimated server cost, to be measured: one typed-array flood fill per decision, roughly 0.1–0.3 ms over at most about 8K standable cells, so a few ms a second for a full room. There is no server tick today, only the 200 ms flush, so the host runs from the flush callback (never at module load, since `MODE=ssg` runs the same bundle), within a budget, with `monitorEventLoopDelay` logged.

## `src/core`

- **Boilerplate**, the interface the rest of the game is built against:
  - `src/core/creature/creatureBrain.ts`: `CreatureBrain` with `createMind`, `decide(mind, surroundings, random)`, `elapse(mind, seconds)` (closed form, for offline catch-up) and `finish(mind, intent, succeeded)`.
  - The types `CreatureMind`, `CreatureIntent` (follow, use_offer, wander, rest), `CreatureSurroundings`, `CreatureOffer` and `CreatureOfferKind`.
- **Rules for its code:**
  - environment-neutral, since it is compiled into both bundles;
  - deterministic, with time and randomness passed in;
  - imports only `src/core`.
- **Wiring.** Both build tsconfigs and the tests tsconfig include it.
- **Guards:**
  - `Edit(...)` deny rules in `.claude/settings.json`;
  - a PreToolUse hook (`protectReservedPaths.js`) that denies shell writes and repo-wide git rewrites reaching it;
  - `autoApproveBash.js`, which no longer approves them;
  - a project rule (`.claude/rules/human-reserved-code.md`);
  - lines in the sweeping skills;
  - a boundary test.

## Design sketch

- **Object type.** A new object type (index 10): non-persistent, owned by its user, with its own category and cap, and added and removed only by the server.
  - Components: `spawnedByMe` rigidbody, emitter and `CreatureController`; `spawnedByOther` receiver; `spawnedByAny` collider, mesh, composer and easing motion.
  - It spawns on the nearest walkable cell in front of the arrival door, since players arrive behind it, inside the wall.
- **Channels:**
  - the intent rides on a server-only metadata key (17), so late joiners get it in the room snapshot;
  - the name rides on `Label`;
  - the server needs a server-originated metadata path that reaches the owner as well.
- **Host.** `src/shared/creature/...` builds the surroundings, calls `CreatureBrain`, leases claims, picks wander cells and publishes activity events for VFX.
- **Navigation.** A walkability util over `Voxel.blockLayerMask`, invalidated by a new room-scoped voxel-edit event.
- **Offers:**
  - the use spot is the floor cell in front of the face;
  - adjacent props of the same kind count as one offer;
  - a target can vanish mid-walk.
- **Persistence.** A new `DBUser` field (migration v6), saved where `playerMetadata` is and also periodically.

## Fixes found along the way

- **F1: any client could add or remove Player objects.**
  - `PlayerObjectTypeConfig.canUserAddObject` and `canUserRemoveObject` returned `IS_SERVER`, which the server's client-facing handlers evaluate as true.
  - Fix: no user may; the server spawns and despawns players through its own entry points; and a client-sent add is stamped with its sender's id and name.
- **F2: an `ObjectGroup` whose objects came from more than 255 distinct users encoded a blob that couldn't be decoded.**
  - The owner count was written in one byte (clamped), yet every owner was still written.
  - Fix: format v8 writes the count in two bytes.
