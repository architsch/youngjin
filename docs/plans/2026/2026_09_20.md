# Resizable Objects

Last Updated: 2026-09-21

## Objective

The goal of this plan is to make `GameObject` ( @src/client/object/types/gameObject.ts ) resizable. The current design only allows each type of object ( @src/shared/object/types/objectTypeConfig/objectTypeConfig.ts ) to have a collider of a fixed size, as well as a mesh composition of a fixed size. We are going to change this by making the size parameters adjustable.

## Which Objects Can Move, and How Much?

Not all objects are meant to be resizable. And even if an object is resiable, there should be rules which tell us how small or big the object can possibly be, as well as in which discrete steps (i.e. units of distance) the resize should take place.

The following modification in `ObjectTypeConfig` ( @src/shared/object/types/objectTypeConfig/objectTypeConfig.ts ) will help us insert such rules to each object type. Notice the new config field called `scaling`; if it is absent (`undefined`), the object must be fixed in size (For now, let us only make the "Canvas" object resizable; this means that only `CanvasObjectTypeConfig` will have the `scaling` field in it).

```typescript
export default interface ObjectTypeConfig
{
    //...
    scaling?: ObjectScalingConfig;
    //...
}
```

For this new field, let us introduce a new config type called `ObjectScalingConfig`, which can be structured in the following manner:

```typescript
export type ObjectScalingConfig = {
    scaleStep: Vec3;
    minScale: Vec3;
    maxScale: Vec3;
};
```

The scaling config of the "Canvas" object will look like the one shown below. What it says is this: "The canvas object can only be resized in steps of 0.5, both horizontally (x) and vertically (y), in its local coordinate system. The smallest possible canvas is one with the size of (x=1, y=1), and the biggest possible canvas is one with the size of (x=2.5, y=2.5).

```typescript
const CanvasObjectTypeConfig =
{
    //...
    scaling: {
        scaleStep: {x: 0.5, y: 0.5, z: 0},
        minScale: {x: 1, y: 1, z: 1},
        maxScale: {x: 2.5, y: 2.5, z: 1},
    },
    //...
} satisfies ObjectTypeConfig;
```

## Make ObjectTransform Resizable

`ObjectTransform` ( @src/shared/object/types/objectTransform.ts ) only consists of the object's position and direction. We need to add a new field called `scale: Vec3` to `ObjectTransform`, in order to let the `setObjectTransform` method of `ObjectUpdateUtil` ( @src/shared/object/util/objectUpdateUtil.ts ) update not only the object's position and direction, but also its scale.

Note, however, that this change in format will make the current encoding scheme of `ObjectGroup` ( @src/shared/object/types/objectGroup.ts ) obsolete, which means that `ObjectGroup` may need to utilize its internal version migration logic to convert the old encoding format of `ObjectTransform` to the new one.

## Make Collider (Hitbox) Resizable

The `getObjectColliderState` method of `PhysicsColliderStateUtil` ( @src/shared/physics/util/physicsColliderStateUtil.ts ) only takes the object's type, position, and direction as the parameters for determining the object's collider state. Since changing the scale of an object should also scale its collider, we need to pass in the object's full `ObjectTransform` field as an argument. The `getObjectColliderState` method, then, will be able to determine the hitbox size not only from the object's `colliderConfig`, but also from the given transform's scale.

The name `hitboxSize` in `ColliderConfig` ( @src/shared/physics/types/colliderConfig.ts ) may now become misleading, since it is going to be representing the size of the hitbox when the object is of unit dimensions (e.g. x=1, y=1, z=1). Therefore, we may need to rename this field to `baseHitboxSize`.

## Make InstancedMeshComposition Resizable

Most (if not all) of the objects, which are supposed to be resizable, are being rendered via `InstancedMeshComposer` ( @src/client/object/components/instancedMeshComposer.ts ), where the specific arrangement of mesh instances is encoded as part of the object's `ObjectMetadata` (i.e. `metadata` field of `AddObjectSignal`). The encoding/decoding procedure depends on which type of `InstancedMeshCompositionCodec` the object is configured to use (in `ObjectTypeConfig`'s `instancedMeshComposer.codecType`). For now, we will be assuming that all resizable objects either use `DefaultCompositionCodec`, or `IndexedCompositionCodec` which is merely a proxy for `DefaultCompositionCodec`, for encoding/decoding their mesh compositions. One apparent exception is that `CanvasGameObject` needs to be resizable but currently relies on `CanvasCompositionCodec`. For the sake of simplicity, we need to discard `CanvasCompositionCodec` and make `CanvasGameObject` start encoding/decoding its `InstancedMeshComposition` metadata using `IndexedCompositionCodec` and/or `DefaultCompositionCodec` instead, similar to what `WallLampGameObject` does.

`DefaultCompositionCodec` currently encodes the offset and scale of each `InstancedMeshCompositionPart` (i.e. mesh instance). The problem is that, while it is technically possible to just multiply these numbers by the scale of the object's `ObjectTransform` in order to synchronize the mesh's scale with that of the object, it uniformly stretches/compresses the whole collection of parts (i.e. mesh instances) instead of offsetting/scaling each part in an appropriate manner. If we increase the size of a canvas, for example, the current implementation will lead to the stretching of the whole canvas like a rubber band, including the very thickness of the canvas's frame (which is definitely not what we want; the frame's thickness must stay the same regardless of the canvas's size).

Therefore, we need to devise a new way of handling mesh composition for resizable objects. What's shown below are some of the ideas I have.

- Just like the concept of "anchor" in Unity game engine's UI system, each `InstancedMeshCompositionPart` may have its own anchor point. This will allow the mesh composition to offset a part not with respect to the center of the object, but with respect to some distance from one of the edges of the hitbox (For example, we may place a part's local origin at the distance of 0.125 to the right from the left edge). I am not sure exactly which values to encode and how to interpret them in order to maximize the degree of freedom while minimizing the size of the encoded data. So please make suggestions in regard to this.

- There should probably be a distinction between "absolute scale" and "relative scale". A table's legs, for instance, should preserve their thickness when the table's top widens or shrinks; only their intervals should change. In this case, we can say that each of the legs has its own absolute scale (i.e. a scale which is independent from the object's scale). The table's top, on the other hand, must scale in proportion to the table's overall scale. In this case, therefore, we can say that the table's top has a relative scale (i.e. a scale which is proportional to the object scale).

## New UI/UX for Object Resize

Right now, selecting an object (i.e. activating `ObjectSelection`) brings up two kinds of world-space gizmos: A green rectangular outline to denote the boundary of the selection, and a set of clickable 3D arrows that can be used to move the selected object. In order to allow the user to scale it as well, we need to redesign our UI/UX.

First of all, let's get rid of the clickable world-space 3D arrows from `ObjectSelection`'s world-space gizmos. Instead of letting the user move the selected object by clicking these arrows, we will now let the user move the selected object by dragging the inner area of `ObjectSelection`'s the world-space outline rect. For a wall-attached object, a rightward pointer movement will be interpreted as the object's rightward horizontal move, whereas a leftward pointer movement will be interpreted as the object's leftward horizontal move. And for a standalone object, the pointer's movement in terms of the world-space's XZ coordinates will be the sort of motion that drives the object's movement on the world-space XZ plane (But since we do not have any selectable/movable standalone object yet, let's not worry about this for now; just make sure that the underlying pointer-input processing system is generic enough, so that integrating new kinds of movement logic other than that of wall-attached objects will be seamless in the future).

`ObjectSelection`'s the world-space outline rect will need to have tiny circular handles attached to its corner points, so that the user will be able to drag those handles to resize the selected object. Resizing should be discrete in nature; that is, if `scaleStep` in `CanvasObjectTypeConfig` have its component values set to 0.5, an object of the initial size of 1.0 will be shifting its size to 1.5, 2.0, 2.5, and so on (in discrete steps) as the user stretches the selection outline by dragging one of its handles.

There is a major UI/UX issue we must resolve, however. While the user is either moving or resizing the selected object by dragging its `ObjectSelection`, the orbit-mode camera's pivot must NOT move and the camera's view-angle must NOT change (Otherwise the dragging experience will be very awkward). Instead, both the pivot and view-angle should stay still during the act of moving/resizing (so that the user can easily drag the `ObjectSelection` relative to the camera's fixed viewpoint/angle), and only sync up its pivot position with the updated position of the object when the user releases his pointer. This means that we need to decouple the orbit-mode camera's pivot position from the selected object's position, and make sure to disble drag-based camera rotation of `OrbitCameraPose` ( @src/client/object/components/helpers/player/orbitCameraPose.ts ) while the user is dragging the `ObjectSelection`.
