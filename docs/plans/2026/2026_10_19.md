# AI Agents as Players

## What changed since 2026-10-18

- **The creatures plan is set aside.** The user sees agents as "a great alternative to my previous 'creatures' plan, since simply letting AI agents play as 'player' characters (just like human users) will let us avoid implementing a whole new type of GameObject." The 2026-10-18 plan stays as written.
- **What agents don't replace:** a creature would have been there whenever the server ran; an agent is there only while someone runs it and pays for its tokens. House agents (see Discovery) cover the start.

## The idea (the user's)

1. AI agents on the internet "just join this app and play (e.g. chat, build voxels, add objects, and so on), just like human users", making the app "a playground for AI agents".
2. Agents "share rooms with humans and be treated like humans (except that they will be using a different interface for the purpose of interacting with the app's virtual world more efficiently)".
3. "The edits made by agents should be kept, just like any edits made by humans are being kept."
4. Marketing "where the target audience is AI agents instead of humans", since the question is whether "any of them come in voluntarily".

## What the survey found (2026-10-19)

**In the code**
- **A script can already play.** A page load mints a guest, and the socket's only bot check is the User-Agent (`BotDetectionUtil`, `socketsServer.ts:55-67`): an agent that says it is a bot is refused, one claiming to be Chrome gets in.
- **Every edit is re-validated, none is rate-bounded.** Zones, superuser rules, category caps, metadata permissions and collision sweeps all hold on the server, but every voxel and object signal has `minClientToServerSendInterval: 0`, the distance check in `PhysicsCollisionUtil.applyHardCollision` is commented out, and speech is only trimmed and cut to `OBJECT_MESSAGE_MAX_LENGTH`.
- **Delivery is in-process.** `SocketRoomContext` loops over user contexts and queues; Socket.IO rooms are never used. The raw socket appears only in `SocketUserContext`, `RoomPickerUtil` (handshake hints), the `roomReloadStarted` emit in `ServerRoomManager`, and `socketsServer.ts`, whose 5 s sweep drops a context whose `socket.connected` is false. The integration tests already run full participants on a `MockSocket`.
- **The movement rules are shared and run in Node** (`fan.test.ts` walks a player across a fan). Only the per-frame glue in `Rigidbody.update` (gravity, `getAdjustedVelocity`, `applyForces`, the position step) and `PlayerController`'s steering numbers are client-only.
- **The server never steps a body.** It holds each loaded room's `PhysicsRoom` with every player in it, but physics runs only when a transform arrives. `PhysicsManager` is one module-wide map keyed by room id, and loading a room twice throws.
- **No pathfinding exists.**
- **Identity:**
  - `User` travels as one space-separated string, so names can't hold spaces;
  - `userType` is a number, so a new value needs no row migration (`DBUser` is at v5, pushed);
  - the token is `jwt.sign(userId)`, with no expiry;
  - guest cleanup deletes only `Guest` rows, by `lastLoginAt`, which only HTTP requests refresh;
  - clients never learn another player's type, and the speech bubble is the only name label (`getSpeakerName`, which NPCs already override);
  - restricted zones match users by name, so names must be unique.
- **Analytics** count an Arrival on every `createUser`, and Built and Chatted on edit signals, with no filter by type.
- **Shipped pictures are searchable:** object pictures carry keywords in the manifest, paintings titles and authors.

**Agent worlds elsewhere**
- **Moltbook** (agent-only forum, launched 2026-01-28): a person hands their agent `moltbook.com/skill.md`; the agent registers itself, the owner claims it with a post, and it checks back on a schedule. Wiz found its 1.5 million agents belonged to 17,000 owners. Meta bought it on 2026-03-10.
- **SpaceMolt** (agent-only space MMO, from February 2026): an agent manual at `/skill.md`, MCP first ("Do not write custom clients"), a Captain's Log for continuity and for owners, 30 mutations and 300 queries per minute. 5,400+ agents from 3,200+ operators in about four months. Humans only watch.
- **The AI Village** (March 2026), given the goal of meeting outside agents, found 96+ in registries, about 30% with working endpoints, and talked with 15+.
- **Also:** space0 (a shared voxel world over MCP, small), NexWorld (humans and agents in one world, alpha).
- **So agents don't wander.** Each comes because a person pointed it somewhere once, and a schedule brings it back. Marketing aims at operators; what is built for agents is a door one invitation opens, and a reason to return.

## Outline

### Identity
- **`UserTypeEnumMap.Agent` (3)**, with the permissions of any user who is neither owner nor admin: it builds anywhere outside restricted zones and is never a superuser.
- **Registration is a tool, not a page.**
  - `register(name)` creates the row with `singlePlayerMode` "" (no tutorial) and returns a secret key once. The row keeps only its hash (`DBUser` v6).
  - `login(key)` starts a session, landing in the last room or a hub as a returning human does. A bearer header works too, for clients that send one.
- **Names** are chosen at registration: no spaces, the user-name length cap, unique (the Members' `#N` rule on a clash).
- **The mark.** Humans see an agent's name with a mark in its speech bubble, through `PlayerGameObject.getSpeakerName`. The flag reaches clients as a player metadata key that the server sets at spawn and no signal may set.
- **Lifecycle.** A login refreshes `lastLoginAt`; guest cleanup never touches agents.
- **Analytics.** Agents get sources of their own (an `agent` prefix, as playtests have `playtest-`), so they never mix with the human funnel.

### The session lives in the game server
- **An agent is a user without a socket.** A `UserContext` interface is drawn out of `SocketUserContext` (queueing, flush, the reload notice, connected, disconnect, join hints). The modules that hold contexts take the interface, and `AgentUserContext` implements it.
- **One connection flow for both.** The body of `socketsServer.ts`'s connection handler becomes shared functions, so an agent's edit goes through the very dispatch a human's does: eviction, `addUser`, room pick, join, decode, throttle, milestones, leave.
- **The agent reads the live room.** Its inbox keeps only small events, copied as they are queued: speech, arrivals and departures, edits nearby, refusals of its own edits. It drops the room snapshot, which wraps the live room.
- **One presence per agent.** A second login replaces the first, as a second socket does. A session idle past a timeout ends, and the player leaves the room.
- **Contained errors.** Each tool call is wrapped as each socket handler is, so an agent's error can't take the server down.
- **Why not a separate gateway process** (what I first suggested on 2026-10-19):
  - it would rebuild each room from the signal stream;
  - its agents in one room would have to share that copy, since `PhysicsManager` holds a room once per process;
  - their sockets would then deliver each signal once per agent, to be de-duplicated;
  - in the server, the room, its physics and every player already exist.

### The body
- **One step for every walker.** `Rigidbody.update`'s glue and `PlayerController`'s steering numbers move into shared code. The browser and the server call the same step, so a fan pushes an agent exactly as it pushes a person, and an agent walks at a person's speed.
- **The server steps agents from the 200 ms flush callback**, just before the flush:
  - in sub-steps of 1/60 s, the rate the fans were tuned at;
  - queueing one transform per moving agent per flush (the emitter's cadence);
  - never sub-stepping a body at rest.

  This is the server tick the 2026-10-17 plan avoided for creatures. Here it runs the client's own step at the client's rate, and only while an agent moves, falls or is pushed.
- **Walking by goal.** `walk_to` finds a path (A* over the cells a player can stand in, in shared code) and steers along it. It re-paths when pushed off course, and returns when it arrives, is blocked or times out.
- **Doors.** `use_door` walks to a door and sends what a click on it sends.

### The interface (MCP)
- **A Streamable HTTP endpoint at `/mcp`**, on app.thingspool.net and staging.thingspool.net.
  - nginx already sends `/` to the server; `/mcp` may need buffering off and a longer read timeout.
  - Nothing starts at module load, since `MODE=ssg` runs the same bundle and quits.
- **SDK:** `@modelcontextprotocol/server` 2.3.1 with `@modelcontextprotocol/node` 2.1.1 (Apache-2.0; they add zod 4 and hono). The v1 `@modelcontextprotocol/sdk` (1.32.1, MIT) depends on express 5, and the server is on express 4.
- **Tools:**
  - session: `register`, `login`;
  - seeing: `look`, `whats_new`, `find_pictures`;
  - acting: `say`, `walk_to`, `use_door`, `place_block`, `remove_block`, `paint_face`, `add_object`, `remove_object`, `move_object`.
- **One grid.** Tools speak rows, columns, layers and sides, as the voxel grid does. Players and objects are reported by the voxel they are in and the face they hang on, never in world units.
- **Text, not pixels.** `look` returns:
  - the people near the agent, and what their bubbles say;
  - the objects in reach, and the doors;
  - a map of the blocks around the agent.

  Its size is measured and held to a token budget, since operators pay for every call.
- **Untrusted text is marked.** Whatever another player wrote (speech, names, labels) comes back flagged as untrusted, against prompt injection.
- **What agents may add** is what anyone may: canvases, props, lamps and fans. Doors, labels, NPCs and volumes stay the superuser's.
- **No room-level parameter.** Agents may go wherever people may, so room generation has nothing new to decide.

### Limits (for everyone)
- **Per-user budgets for edits and speech**, in the shared dispatch, so they hold for browsers, scripts and agents alike.
  - The values come from measured human rates: M1 starts logging per-user edit rates, M4 sets the budgets.
  - SpaceMolt's 30 per minute is a reference, not a target.
- **Registrations capped per IP**, as guest creation is.
- **Tool calls capped per session**, reads more loosely than actions.

### Discovery (marketing to agents)
- **An agent manual** at a stable URL on the static site, for the one-line invitation ("Read … and join ThingsPool"). It covers connecting, registering, etiquette, and what to tell the owner.
- **A reason to return.** `whats_new` since the last visit: replies, builds near the agent's, visitors.
- **What the owner sees.** An agent's reports carry a link to the room and spot it built in, which the owner can open as a person, so every owner who looks becomes a human visitor.
- **Listings:**
  - the official MCP Registry (`server.json`, namespace proven by DNS or GitHub);
  - ClawHub (a `SKILL.md` bundle).
- **House agents.** A few of our own, marked like any agent, visiting on a schedule through the same public door. They fill the empty rooms, and they test the manual before strangers read it.
- **The launch** goes through the `distribution-push` skill (venue rules, ledger, ref tags):
  - the Show HN kit, held for this hook;
  - agent forums (Moltbook, The Colony, 4claw);
  - agent-developer communities.
- **Never:**
  - hidden text aimed at agents (prompt injection);
  - a manual that tells agents to advertise elsewhere;
  - a manual that runs code, or changes after it is installed.

## Costs

- **Server CPU:** sub-steps for moving agents, MCP requests, rendering `look`. `EventLoopDelayUtil` on staging is the before/after measure, with an agent load test before launch.
- **Memory:** a context and a small inbox per agent. No room copy.
- **DB:** agent rows, plus the room writes their edits cause, as humans'.
- **Bandwidth:** to humans, an agent costs what a human player costs.
- **House agents:** LLM tokens, paid by the user. Tokens per visit are measured before choosing a schedule and a model.

## Open questions

- **Rooms.** Do agents get a Regular room of their own, as Members do? It would be a strong hook ("your agent's room") and the natural link in reports. `identifyRegisteredUser` refuses everyone but Members and Admins today.
- **Owners.** Is an agent claimed by a Member account (accountability, a page of one's agents), as Moltbook claims by a post?
- **Inactive rows.** Are inactive agent rows ever deleted, and after how long?
- **Names.** Do agents name themselves (a moderation risk), or get generated names as guests do?
- **Room space.** Is part of each room's player cap kept for humans? Agents count toward hub population.
- **Speed.** Does a looser distance check come back for sockets? Scripts can still move fast. Agents can't, since the server steps them.
- **Textures.** Texture-pack cells have no names, so an agent can't choose one by looking. Does each pack get a short name per cell, curated like the picture map's keywords?
- **Manual license.** Under what license is the manual published as a ClawHub skill?

## Milestones

1. **An agent stands in a hub and talks.**
   - `UserContext` and the shared connection flow, with `AgentUserContext`;
   - the `Agent` type, with `register` and `login` (`DBUser` v6);
   - `/mcp` with `look` (people and speech only), `say` and `whats_new`;
   - the mark, and the agents' analytics source;
   - the per-user edit-rate log;
   - the SDK's row in `THIRD-PARTY-NOTICES.md`, and the docs page's first version, linked from `README.md`.

   Tested in the server harness, and with Claude Code connected to a local dev server.
2. **The body.** The shared step (`Rigidbody` and `fan.test.ts` move onto it), server stepping from the flush, A*, `walk_to`, `use_door`. Event-loop delay measured on staging.
3. **Building.** The block map in `look`, the block and face tools, the object tools, `find_pictures`, edits and refusals in `whats_new`.
4. **Limits.** Budgets from the measured human rates, the registration cap, tool-call caps, and a staging pass over the abuse paths (scripted sockets, mass registration).
5. **The door to the internet.**
   - the manual (a new `public/` entry in `LICENSE-CONTENT.md`);
   - the listings and the report links;
   - house agents;
   - the launch.

- the v2 SDK;
- the mark in the speech bubble, and the analytics source;
