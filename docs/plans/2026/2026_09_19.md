# Camera Distance Logic Simplification for Lights

Please work on the following task:

Right now, the headlight's range, the fog's fadeout range, and the far plane's distance get pushed away to a greater distance when the orbit-mode camera moves far away from its pivot.

While this helps the edit-mode user view the whole scene with enough light and clarity, it does not accurately depict the way in which the room is being lit under ordinary circumstances (i.e. first-person camera mode). Therefore, we should abandon this distance-based range scaling algorithm (for the sake of both simplicity in logic and accuracy in lighting), and apply the following rules instead:

- Let's say that there is a threshold distance called X (This can be a constant of a decent value, such a 8).
- If the orbit-mode camera's distance from its pivot is less than or equal to X, the reference point for headlight positioning and fog distance calculation must be the same as the camera's location (same as in firstPerson-mode).
- If the orbit-mode camera's distance from its pivot is greater than X, the reference point for headlight positioning and fog distance calculation must be `pivotPosition + X * normalized(cameraPosition - pivotPosition)`.
- The headlight's range, the fog's fadeout range, and the far plane's distance must NEVER change no matter how how away the orbit-mode camera is from its pivot (The far plane's distance should simply be fixed at a value that is large enough to let all parts of the room be rendered even when the orbit-mode camera is zoomed out as much as possible from a pivot that is at the farthest corner of the room).

# Category System for Objects

Right now, each type of object has its own `maxCountPerRoom` (see @src/shared/object/types/objectTypeConfig/objectTypeConfig.ts ), so as to prevent users from bloating the room with an unreasonably huge number of them.

Eventually, however, we will need to let objects of different types count up the same number as they spawn, if they happen to belong to the same general category. For example, if we have multiple types of "lamp" object such as "WallLamp", "CeilingLamp", and "StandaloneLamp", and if the goal is to limit the maximum number of lamps inside the room regardless of their placement types, we will need to be counting up the same number which corresponds to the "Lamp" category.

So, let us introduce a new property called "category", let each `ObjectTypeConfig` have it, and enforce both the server and client to suppress the addition of any object whose category's current count has reached its maximum. Keeping a dictionary of count values in `Room`'s `ObjectGroup` and updating/checking it in `ObjectUpdateUtil`, I think, is the best way of handling this (But feel free to suggest a better solution if you have one).
