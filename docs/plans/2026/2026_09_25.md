# Using Canvases to Represent Common Objects

Last Updated: 2026-09-27

## Phase 1

### Problem

I just realized that there is something missing in this game.

Currently, we have a bunch of textures we can apply to voxel-quads (see @src/client/ui/components/hud/selection/voxelQuadTextureOptions.tsx ), and a bunch of old paintings which can be put on walls in the form of `CanvasGameObject` (see @src/client/object/types/canvasGameObject.ts ).

None of them, however, represents ordinary objects which people use on a daily basis - including books on a bookshelf, soda cans/bottles inside a transparent fridge, goods in a grocery aisle, a mirror, front face of a microwave, front face of an oven, drawers, computer monitor, TV, and so on. Implementing all these objects as realistic 3D models is, I think, not going to be a good decision because: (1) It is hard to implement them, and (2) It hurts the GPU's performance too much.

### Solution

Thus, my idea is to leverage the existing `CanvasGameObject` as much as possible for rendering real-life objects (such as home appliances, electronic gadgets, pile of consumer products, etc) as combinations of 2D images and voxel blocks. A microwave oven, for instance, can be represented as an image (canvas) of the front face of a microwave that is placed upon a stack of 2 voxel blocks, and a bookshelf can be represented as a couple of "book collection" images (canvases) placed upon a stack of voxel blocks that have wooden textures on them.

The only changes we need in order to implement the aforementioned functionality are listed below:

1. Make `CanvasGameObject` attachable to floors and ceilings, not just walls.
2. Make each `CanvasGameObject`'s flat surface (image + frame) rotatable by 90 degrees. This can be realized by adding a new key in ObjectMetadata ( @src/shared/object/types/objectMetadataEntry.ts ) whose base-94 encoded character value can either refer to 0-degree rotation, 90-degree rotation, 180-degree rotation, or 270-degree rotation (Let's give a generic name to this key because we may, in the future, want to use this key for other object types as well).
3. In @src/client/ui/components/hud/selection/canvasEditOptions.tsx , then, we will need to add a new "rotate" IconButton (with the icon showing a "round arrow", oriented clockwise if you are going to rotate the canvas clockwise, or counter-clickwise if you are going to rotate the canvas counter-clockwise) which, when clicked, will rotate the canvas by 90 degrees. The purpose of this rotation is to let the user change the orientation of the canvas when it is attached to a horizontal surface (i.e. floor or ceiling).
4. For @src/server/ssg/builder/imageMapBuilder.ts , we will need to have a new canvas image folder (in `public/app/assets/canvas_images`) called "2" which will contain not a collection of paintings by artists, but a bunch of royalty-free images of the aforementioned "ordinary objects" that are taken from the front view (I'm not sure where to find such images, so please help me find them and save them as `.webp` files. All these images, by the way, should preferrably have aspect ratios which can tightly fit inside at least one of the possible aspect ratios of the canvas object when no frame is present (without any margin)).
5. Inside @src/client/ui/components/form/imageListChooserForm.tsx , then, we will need to show a list of "ordinary object" images via a separate tab. The first tab must be the one listing the images in folder "2", and showing the display-name "Objects". The second tab must be the one listing the images in folder "1", and showing the display-name "Arts".
6. When a new `CanvasGameObject` is manually added by a user, a random image in folder "2" should be applied and the frame option should always be "no frame" by default.

## Phase 2

During Phase 1, Claude implemented a working prototype of a framework which now let us use `CanvasGameObject` to render frontal views of some of our common, everyday objects (such as electronic appliances, grocery aisles, bookshelves, etc). What's shown below are some of the additional improvements which need to be made.

### Problem with Rotation

A wall-attached canvas's image, when moved over to either the floor or ceiling, may end up being turned by some multiple of 90 degrees in angle (The amount of rotation depends on what the direction of the wall was). This is not supposed to happen because it does not feel intuitive. I guess the solution is to add a logic which automatically adjusts the angle of the canvas whenever its direction of attachment changes (i.e. it moves over from a wall to a floor/ceiling or from a floor/ceiling to a wall).

### Delay in 90-Degree Rotation

There is also a significant delay between the moment at which the user clicks "rotateCanvasButton" and the moment at which the result of the rotation gets reflected in world space. Such a delay should go away.

### Image Resolution

Some of the images need to be quite large in size, yet the problem is that huge canvas images tend to have way too low resolutions. The reason is that, unlike `LabelGameObject` which uses a dynamic texture-atlas area allocation logic which adaptively reserves small areas for small labels and large areas for large labels, `CanvasGameObject` simply allocates a cell of a uniform size within the texture-atlas. In order to prevent the image from looking too pixelated, we have to start dynamically allocating texture areas whose sizes are proportional to `CanvasGameObject`'s hitbox sizes. This may also imply that the texture-atlas of `CanvasGameObject` will need to be significantly larger than it is today, since canvases of large sizes will end up occuyping way more cells in the atlas.

(Implementation tip: Let `CanvasGameObject` reuse the same texture allocation system which `LabelGameObject` is currently using, instead of having its own separate system. Let's also make sure that multiple `CanvasGameObject`s with the same `ImagePath` all point to a single allocated region in the texture-atlas, instead of allocating the same exact image in multiple spots.)

### Image Scale Preservation

Right now, all canvas images stretch/shrink to fit themselves tightly within the inner borders of their frames (or the boundaries of the canvas object's footprint, in case of no frame), while preserving their aspect ratios. @docs/geometry/texture.md explains how this works.

For sake of scale-preservation in the images of ordinary objects, however, we need to add an option to preserve the image's original size in pixels (so that it will never stretch/shrink itself when the canvas resizes; pixels which happen to overflow the canvas's world-space boundaries will simply get cut off). If this option is set, the texture allocation algorithm will need to be simply based on the image's original size instead of the canvas's hitbox size. And this also implies that each image's size in pixels will need to be discrete in nature (i.e. integer multiples of the smallest atlas cells, each of which corresponds to a square of width 0.5 in world space), so that we won't end up wasting tiny gaps in space between regions of allocation.

(Implementation tip: The aformentioned option can be added as a boolean field in `ImageMetadata` (i.e. @src/shared/graphics/image/types/imageMetadata.ts ), which corresponds to an entry in the `ImageMap`. All images of ordinary object will probably have this option turned on, since stretching/shrinking the appearance of an ordinary object (such as a tool, consumer good, etc) will make it look too awkward).

### Sampling of Source Images

I see that you basically took the whole photos I referenced and only cut off their boundaries. Some of the photos, however, are more of collections of samples, each of which need to be taken out as a separate image (such as each distinct corner of a grocery aisle, etc). So please feel free to sample each distinctive part of a source image and save it as a separate asset.

### Play-Mode Click Interactions

It will be a waste of precious resources if we use our new canvas images (i.e. images of ordinary objects) just for cosmetic purposes. Some objects, including vending machines, bookshelves, grocery aisles, refrigerators, and so on, are meant to be interactable during gameplay. So, let us have a new map (dictionary) which routes `CanvasGameObject`'s `onClick` callback to each `ImagePath`'s own custom callback (Only when `GameMode` is set to "play", and not when it is set to "edit"). These callback functions can be empty for now.

(Implementation tip: `CanvasGameObject` class can have its own override for `GameObject`'s `onClick` method. Inside this override, we can try executing the base class's `onClick` first and then execute the aforementioned custom callback function in case the base method call fails. This means we may need to convert the return type of `GameObject`'s `onClick` method from `void` to `boolean`).

### Image-Editing Tool

In a manner similar to how `dev/scripts/compositionEditor` is devised, we need to implement an "image map editing tool" which will help us quickly create/edit/delete the entries in each `ImageMap` by opening up any image files from the local machine, taking samples by selecting portions of those images, turning their unnecessary background colors into transparent pixels, manifesting each polished sample as the `ImageMap`'s new entry, and tweaking the parameters the entry such as the image's scale (in pixels) in the actual game (i.e. size of the region in the texture-atlas that the image must reserve), its image-fitting option, title, author, etc.

This new tool, in addition to allowing us to create/edit/delete `ImageMap`'s entries, should also automatically create/edit/delete these entries' corresponding image files in `public/app/assets/canvas_images`.

## Phase 3

I reviewed the result of Phase 2. What's shown below are my follow-up suggestions:

### Notes on Code Architecture

- `playModeClickCallback.ts` and `playModeClickCallbackEntry.ts`, in my opinion, should not be located at `src/client/object/types/`. This directory is for either subclasses of `GameObject` or implementations of `ObjectTypeClientConfig` (Maybe I should also create a sibling directory of `objectTypeClientConfig` called `gameObject` and put all the subclasses of `GameObject` there. If you can do that on your own, I will really appreciate it). The main issue is that the concept of "playModeClickCallback" isn't strictly tied to gameObjects; play-mode clicks might be applicable to meshes/hitboxes which do not necessarily belong to gameObjects, you know. So, I would say that moving `playModeClickCallback.ts` and `playModeClickCallbackEntry.ts` into `src/client/graphics/types/` feels more appropriate.

- Let's create a new directory called `texture` inside `src/client/graphics/types` and move all the texture-related files in `src/client/graphics/types` over there. This will help us organize things more neatly.

- The presence of @src/server/ssg/data/canvasImageMapSeed.ts feels a bit awkward. If `src/server/ssg/data` is the appropriate for such a type as `CanvasImageMapSeed`, why don't we have something similar for the voxelTexturePack imageMap at the same location? My suggestion is to just directly write down the definition of `CanvasImageMapSeed` within its usage in the function call of @dev/scripts/imageMapEditor/node/buildCanvasImageMap.ts , rather than explicitly declaring it as a named type inside a separate file (since `buildCanvasImageMap.ts` is the only place where `CanvasImageMapSeed` is being used). But please push back if you have a better idea.

### Canvas Sizing Constraint

Your previous suggestion turned out to be a better decision. While I did decide to just let the canvas object be resizable regardless of the fixed-size image's own pixel size (i.e. "ordinary object" images), I soom realized that it is way to prone to human errors. Hence, I made a new design choice; from now on, we will simply make all "ordinary object" images either occupy a 1x1 area, 1x0.5 area, or 0.5x1 area in world space (This means that `CanvasGameObject`'s minimum size will need to be 0.5x0.5; you don't need to introduce any additional rules besides this, I guess, because the rest is just design preference which we can just enforce on ourselves when editing the ImageMap). Anyways, I think it will be appropriate for us to just force each fixed-size image to have a fixed canvas size (i.e. size in world space) which matches the image's own size. This also implies that the image-chooser's selection UI and other related UI elements will need to be disabled and both client-side and server-side validation logic will need to be updated to ensure that the canvas size is always synced up with that of the image size IF the image is of a fixed-size.

### Requests for ImageMapEditor

- I would like to have an option to change the source image of the currently selected imageMap entry, so that I will be able to resample from a source image that is different from the previous one. Also, I would like to have a separate "source image collection" directory within the project folder and have it accessible via a tab (page) in the imageMap editor, so that I will be able to separately upload source images there and select them when either creating a new imageMap entry or modifying the source image of an existing imageMap entry. This will be much more convenient than browsing a file directly within my local machine every time I want to fetch a source image file. And it will be even better if I can upload a new source image in this "source image collection" directory via the image's URL, and have it automatically carry over to the "source" field of whatever imageMap entry it is being applied to (p.s. How are the source images even being saved/retrieved right now? Are the ones I see in the imageMapEditor just references to my local machine's image files, which were browsed before?)

- The background-erasing functionality is either way too sensitive or too insensitive in most cases. Please give me an option to tweak the cutoff threshold value that is being used to determine which pixels are background pixels and which aren't. Also, it will be even better if you give me tools which I will be able to use to manually turn parts of the image into transparent regions (e.g. erasers, select-by-color tools, etc).

- When the currently selected imageMap entry has been modified but not saved, it should let the user click a "discard" button to cancel all the unsaved modifications (with a confirmation dialog, so that an accidental click of the "discard" button won't screw things up).

- It will be better if I have an option to slightly rotate the sampled image, so as to deal with images that are slightly tilted (Colors of near-border pixels, which happen to emerge due to such a rotation, should have colors which are similar to those of their neighboring pixels).

- When the sample region's aspect ratio is different from that of the allocated area in the texture atlas (i.e. "Cells across" & "Cells down"), we shouldn't force-fill the allocated area exhaustively by changing the sample region's aspect ratio; instead, we should preserve the sample region's aspect ratio, simply fit it inside the allocated area as much as possible based on that fixed aspect ratio (like what the "Arts" canvas images are doing to fit themselves within the canvas's frame without any change in the aspect ratio - see @docs/geometry/figures/texture_fitting_in_region.jpg ), and fill the margins with either the image's background color (if the image doesn't contain transparent pixels) which can be obtained by computing the average color of the boundary and near-boundary pixels, or transparency (if the image contains transparent pixels).

- Changing the size of the currently selected imageMap entry's sample region, or saving the current imageMap, feels a bit too laggy due to the presence of enormous delays (especially when the source image is huge). Is there a way to reduce this kind of performance issue?

- It will be even more fabulous if you can add options to tweak the sampled image's overall brightness, contrast, saturation, and other general image properties (so that I won't need to open up the source images in Gimp and adjust the colors there in order to match the color schemes with that of the other in-game image assets).

## Phase 4

I reviewed the result of Phase 3. What's shown below are my follow-up suggestions:

## Further Improvements

- It looks like the image resolution of 128px per the distance of 1 in world space makes the image too hard to discern. Let's increase it to 256px, like you've previously suggested.
- Let's just allocate the maximum area of 256x256 pixels per canvas image (both for object-images and art-images), which is typically of size 1x1 in world-space in case of object-images. For 1x0.5 and 0.5x1 object-images, the areas of allocation will be 128x256 and 256x128. The reason is that we are no longer letting object-images occupy more than the distance of 1 in world space. This will let us save far more space for texture allocation (But let's keep the current size of the atlas which is about 4096px, and simply increase the maximum number of canvases which can be installed within the room, so as to let us fill the room with far more canvases than before). Anyways, this new change will make the allocation-area sizing scheme of canvas images different from that of the label text images, but I would like you to preserve their shared layer of abstraction as much as possible and only differentiate their allocation-area sizing schemes by means of parameterization. This will help us keep the codebase as simple as possible by not having separate texture-allocation systems for two very similar use cases.
- When the user manually creates a new `CanvasGameObject`, let's initialize its image/frame to be either: (1) A random object-image with no frame, or (2) A random art-image with a random frame (For this new randomization logic, we will need to mark each imageMap subfolder as either "can have a frame initially" or "must not have a frame initially", so that any new canvas's image in a subfolder which belongs to the latter option will initially come with no frame. This does not mean, though, that frames aren't allowed for this kind of image; if the user wants to give it a frame, let him do so).
- The imageEditor only allows me to apply brushes (such as erasers) to the tiny preview image of the sample. Please add a way to magnify the view of the sampled image which I am editing by hand.
- Please make each "source image" entry in the imageEditor display the URL from which it originated (unless I just registered the entry by pasting a file in my local machine). Will be even better if we can have a "copy" button right next to it which, when clicked, will copy the URL to the clipboard.
- Will be great if I can mark each imageMap entry (imagePath) as "disabled", so that the entry that is disabled will be ignored during the final imageMap bundling (`canvasImageMap.ts` generation) process. This is because there are times when I just want to get rid of an ugly image asset from the game without screwing up the imagePath order of the rest of the entries, and then come back later on to replace the ugly image with a more decent-looking image (which I will then be able to "enable" again to show it to the public).

## Image Asset Revisions

I revised my list of suggested URLs for source images, please replace your current source images with the ones listed in the snippet below, resample them to extract decent object-images out of them, and apply them to the imageMap's entries. Feel free to overwrite the content of any of the existing entries which do not look good for the guidelines I provided below.

- Guidelines:
    - Each distance of 1 in this game's world-space should roughly correspond to about 40 centimeters in real life. Please sample your source images based on this scaling standard. Objects must not appear to be either too huge or too small.
    - Make sure that each sampled image will make sense to the viewer (i.e. appear to be realistic) when it is being displayed within the game - that is, when it is being rendered as a flat surface. This means that an overly convex form, which is not supposedly a part of a concave space (e.g. inside of a fridge, inside of a shelf, etc), ought not to be sampled because it will look too unrealistic.
    - Each sampled image should be fairly distinct in nature (e.g. has boundaries, is a standalone object or a collection of objects, etc).
    - Please don't discard (skip) the existing imageMap entries (i.e. imagePaths' index numbers). Just override their outdated imageMetadata with new ones.
    - Feel free to erase backgrounds of the sampled images and make them transparent on your own, within the imageEditor (unless it be more appropriate to preserve the backgrounds - such as when the sampled image is a distinctively self-contained area such as the inside of a box, a transparent fridge, a shelf, a grocery aisle, etc).
    - Feel free to rotate the sampled images if they are tilted, and feel free to adjust their overall brightness, contrast, and other color properties if they are either too dim, too extreme in qualiy, etc.

## Phase 5

I reviewed the result of Phase 4. What's shown below are my follow-up suggestions:

### Game Mechanics

- When the size of a `CanvasGameObject` is 1 across one axis and 0.5 across the other axis, it always assumes that it is only capable of expanding in one of the two possible directions (and not the other direction) when the user tries to change its image to one which requires the size of 1x1. For more degrees of freedom, `CanvasGameObject` should take into account of all 4 possibilities during the validation logic:
    1. The case in which 1x0.5 becomes 1x1 by growing upward.
    2. The case in which 1x0.5 becomes 1x1 by growing downward.
    3. The case in which 0.5x1 becomes 1x1 by growing rightward.
    4. The case in which 0.5x1 becomes 1x1 by growing leftward.
- During the "edit" mode, let's allow the user to move objects (e.g. canvases, lamps, labels, doors, etc) not in the unit of 0.5, but in the unit of 0.25. This will allow the user to tightly place objects of size 0.5 at the corners (of voxel blocks and other objects) without any margin of size 0.25.

### ImageMap Editor

- Sampled image needs both an elliptical and rectangular selection tool (optionally with rounded edges of a customizable radius) which lets the user make all the pixels outside of the selection either transparent or of a customizable background color. This shaped-based transparency filter should be able to be applied additively to the existing "smart transparency filter" which automatically converts background pixels into transparent ones. That is, if both filters are present, a pixel should become transparent if at least one of them marks it as transparent.
- Both "Objects" and "Arts" imageMap entries should support sampling, color adjustments, source-image fetching, and all other editing options (not just "Objects" entries), unless the peculiarities of the "Arts" images make it strictly necessary to hide some of those options. (p.s. This will also let you simplify your editor codebase because it will get rid of the necessity to apply two different rules to two different image subfolders).

## Phase 7

I reviewed the result of Phase 6. What's shown below are my follow-up suggestions:

### Refactoring of Object Types

- It turned out that letting `CanvasGameObject` handle both object-images (i.e. images in subfolder "2") and art-images (i.e. images in subfolder "1") makes things too confusing. Let's just create a new type of `GameObject` called `PropGameObject`, which functions like `CanvasGameObject` but exclusively deals with images in subfolder "2", while the existing `CanvasGameObject` exclusively deals with images in subfolder "1". I hope this will be a fairly simple refactor, since the only major logic involved here is to let `CanvasGameObject` and `PropGameObject` pick (or filter out) imagePaths based on their subfolder names.
- This may also mean that some of the file names and folder names (such as "canvas_images", "canvas_image_sources", etc), as well as variable/function names, will need to be revised for semantic clarity, since those will no longer solely belong to `CanvasGameObject`.
- p.s. Don't worry about version migration or anything like that; I haven't committed/pushed any of the implementations of the current feature work (i.e. `2026_09_25.md`), so version conflict won't be an issue here.

### ImageMap Editor

- When the user disables the "Take out the background" checkbox and then enables it again, the Tolerance and Edge Stop slider values go back to their defaults. These values should be recovered to what they were when the chechbox was disabled.
- There is no way to adjust the size of the rectangular/elliptical selection (in `Sample -> Selection`) adjustable after creating it by dragging the somewhere on the sampled image. Please make it adjustable.
- It will be much better if the user can tilt the current rectangular/elliptical selection (in `Sample -> Selection`), so as to be able to select, say, a diamond-shaped region and so on. Also, let's make a "list of selections" and let the user apply multiple selections wihin the same sampled image, so as to let him erase the image's background using multiple shapes (For example, an octagonal "Stop" sign will require us to make two rectangular selections in order to erase its background - one axis-aligned, and the other one tilted by 45 degrees in angle). The general UI flow associated with such a list will be reminiscent of that of a typical "list of layers" in an image editing software such as Gimp, where clicking one of the list items focuses the selection to which it corresponds.
- Right now, when the sampled image's aspect ratio happens to differ from that of the texture-atlas cell allocation region (i.e. `Sample -> Size in the game -> Cells across & Cells down`), margins of the exact same size are being padded onto both sides (either right/left or top/down). For more degree of freedom, the user should be able to set the ratio between these two margins, so as to let him stick the object either to the right(bottom), left(top), or the center, or any arbitrary spot. In fact, it will be even better if the user can pad extra margins around the sample image just to make it smaller relative to the world-space area which it is supposed to occupy; for this, let's simply add 2 numerical text input fields which will let the user enter two values: (1) The percentage of the extra horizontal margin with respect to the horizontal axis, and (2) The percentage of the extra vertical margin with respect to the vertical axis. Both of these values, of course, will need to be 0 by default.
