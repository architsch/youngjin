# Test Scenario Coverage

A map of what each suite in `tests/integration/scenarios/` covers. The test names inside each file are the detailed catalog, so read the file itself before extending it.

## Server gameplay (through the harness)
| Suite | Covers |
|---|---|
| `connection.test.ts` | connect and disconnect (with or without save), Case A/B reconnects, rapid cycles, metadata on join and chat |
| `room.test.ts` | loading on first join, joining a loaded room, missing rooms, switching and saving, unloading on empty, graceful shutdown |
| `room-population.test.ts` | player cap and near-full margin, rejection signal, hub picking by band, app-start destination, leaving single-player, refresh and restart |
| `room-ownership.test.ts` | owner and visitor enter/exit, room switching with ownership |
| `object.test.ts` | adding, removing and moving objects, with rollbacks, and the sizes a client may ask for |
| `voxel.test.ts` | add, remove, move and texture operations with rollbacks, the boundary wall, wall attachment at every size, the lamps a block holds up and down, the encoded grid; blocks of other shapes than whole put up, reshaped and moved, each told to the others and each refusal (a shape no block has, a taken or missing cell layer, a canvas or a door left without its wall) answered with what the cell layers hold |
| `signals.test.ts` | multicast excludes the sender, a refused voxel edit answered to its sender alone with the cell layer's block or its absence, no cross-room leaks, a batch relaying its signals in the order they were made whatever their types, authoritative transform correction reaches everyone |
| `permissions.test.ts`, `permissions-extended.test.ts` | anyone may build in Hub and Regular rooms, and ownership is never a per-operation condition |
| `restricted-zones.test.ts` | server enforcement for blocks (added, removed, reshaped, moved in or out), faces and persistent objects, superuser identity, zone-list validation, persistence, the sandbox's exemption |
| `door.test.ts` | superuser-only door operations, metadata sanitizing, vertical placement, the whole blocks a door needs behind it, spawn selection (including a door found by its label as read) |
| `ghost-mode.test.ts` | the `AdminPrefs` codec and untrusted input, admin-only ghost mode on one's own character, relay, saving and restoring it, dropping it after a demotion |
| `lamp.test.ts` | lamp permissions (no stored look), the per-category room cap (on load, after a removal, and against other categories), emitted light, the glow following the light at every size, the sizes (exactly the scale grid, no corner handles), each size's own pre-encoded look and the look following an untrusted scale, and a player standing on a floor lamp |
| `state-persistence.test.ts` | metadata and voxels across reconnects, empty-room saves, extended invariants, shutdown |
| `room-file.test.ts` | the room file (its layout, round trip, players left out, any room taking it, older contents converted, and what it refuses: other files, cut or padded ones, newer formats), and loading one over a live room: voxels, persistent objects and settings replaced (the hub's join priority kept), players kept and arriving behind the file's door, physics rebuilt, settings stored before contents, users held from before the first write until the room is sent whole (queued signals dropped, a latecomer sent it once), one file at a time, and each way it can fail |
| `race-conditions.test.ts` | RC1–RC12: concurrent joins, join during unload, simultaneous edits, transitions, disconnects, churn, shutdown, latency stress, metadata-cache race |
| `property-based.test.ts` | random action sequences across weight profiles (with and without latency), every room's grid staying storable through them (see `checkVoxelGridConsistency`), block edits checked against a model of their rules that shares no code with them (what the server holds, relays and answers), gameplay persistence, room volume geometry, integer range math |
| `single-player.test.ts` | single-player server contract, wire format, local generation, the tutorial's edit-mode opening, the face it asks the user to pick out and builds against, its lock on undo and redo, step graph |
